## 11.1 V2 · 命令框架

### 11.1.1 三个必须先定下来的设计决定

**决定 1：命令的「行为」用代码注册，「描述」用配置覆盖**

TS 版把 `handler: 'builtin:help'` 写在配置里，靠字符串查表。Go 里照抄的后果是：一个字符串打错只在运行时暴露，且 IDE 无法跳转。

```go
// ✗ 不推荐：配置里写 Go 函数名
// commands:
//   definitions:
//     - name: help
//       handler: builtin:help

// ✓ 推荐：代码定义行为，配置只覆盖展示与开关
// commands:
//   definitions:
//     - name: help
//       enabled: true              # 可关掉
//       description: 自定义描述      # 可覆盖
```

**决定 2：命令解析失败要回退到 AI，而不是回「未知命令」**（R18）

用户打 `/ 帮我写个函数`、`/xyz` 时，最不打扰的行为是**当成普通消息走 AI**。只有「首个 token 完全等于已注册且 enabled 的命令名」才视为命令。

**决定 3：命令轮 `status = 'filtered'`，绝不进 AI 上下文**（R4）

这是 V1 建表时就留好的缝（§8.7 缝 3）。

### 11.1.2 接口（`internal/chat/command/handler.go`）

```go
package command

type Handler interface {
    // Name 与配置里的 name 对应，用 ASCII 短横线
    Name() string
    // Run 执行。返回的文本将被原样发给用户（分段由 Outbound 负责）
    Run(ctx context.Context, c *Call) (string, error)
    // NeedLLM 用于健康检查/文档：说明该命令是否依赖模型
    NeedLLM() bool
}

// Call 一次命令调用的上下文。
type Call struct {
    Text    string                 // 完整原始文本
    Args    []string               // 已按空格切分的参数
    RawArgs string                 // 参数原文（保留空格，给 /prompt 用）
    Conv    platform.ConversationKey
    Sender  platform.Sender
    ConvID  int64
    Def     Definition             // 配置里的定义（含 usage/arg 校验规则）
    Log     *slog.Logger
    Cfg     func() config.Config    // 命令可能需要读写配置
    Store   Store                   // 命令需要读写数据（V2 的 /prompt）
}

// Definition 命令定义（可由配置覆盖展示层）
type Definition struct {
    Name        string
    Description string
    Usage       string
    Enabled     bool
    Args        []ArgDef
}

type ArgDef struct {
    Name     string
    Required bool
    Values   []string   // 非空则校验枚举
}
```

### 11.1.3 `parse.go`（纯函数，测起来最舒服）

```go
package command

// ParseResult 解析结果。IsCommand=false 表示应该回退给 AI。
type ParseResult struct {
    IsCommand bool
    Name      string
    Args      []string
    RawArgs   string
    Handled   bool   // 命令名存在但被禁用/解析异常
    Hint      string // Handled=true 时给用户的提示
}

// Parse 解析斜杠命令。
//
// 规则（R18）：
//  1. 归一化：去首尾空白、全角斜杠 → 半角
//  2. 必须以半角 '/' 开头
//  3. 首个 token 必须**完全等于**某个已注册且 enabled 的命令名，否则回退 AI
//  4. 参数按空白切分；RawArgs 保留原文
func Parse(text string, defs map[string]Definition) ParseResult {
    norm := strings.TrimSpace(text)
    norm = strings.ReplaceAll(norm, "／", "/")     // 全角
    norm = strings.ReplaceAll(norm, " ", " ")      // 不换行空格

    if !strings.HasPrefix(norm, "/") {
        return ParseResult{}
    }

    // 按第一个空白切开：命令名 + 参数原文
    head, rawArgs := splitFirst(norm[1:])
    name := strings.ToLower(head)

    def, ok := defs[name]
    if !ok {
        return ParseResult{}                        // 未知命令 → 回退 AI
    }
    if !def.Enabled {
        return ParseResult{IsCommand: true, Name: name, Handled: true,
            Hint: fmt.Sprintf("命令 /%s 当前已关闭。", name)}
    }

    args := strings.Fields(rawArgs)
    if msg := validateArgs(args, def); msg != "" {
        return ParseResult{IsCommand: true, Name: name, Args: args,
            RawArgs: rawArgs, Handled: true, Hint: msg}
    }
    return ParseResult{IsCommand: true, Name: name, Args: args, RawArgs: rawArgs}
}

// splitFirst 在第一个空白处切成两段。
func splitFirst(s string) (head, rest string) {
    if i := strings.IndexAny(s, " \t\n"); i >= 0 {
        return s[:i], strings.TrimSpace(s[i+1:])
    }
    return s, ""
}

func validateArgs(args []string, def Definition) string {
    for i, a := range def.Args {
        var v string
        if i < len(args) {
            v = args[i]
        }
        if a.Required && v == "" {
            return fmt.Sprintf("❌ 缺少必填参数: %s\n\n用法: %s", a.Name, def.Usage)
        }
        if v != "" && len(a.Values) > 0 && !slices.Contains(a.Values, v) {
            return fmt.Sprintf("❌ 无效参数: %s\n\n允许的值: %s", v, strings.Join(a.Values, ", "))
        }
    }
    return ""
}
```

**必测的 6 个用例**（直接对应 R18 的验收）

| 输入 | 期望 |
|------|------|
| `/help` | `IsCommand=true, Name=help` |
| `/help me 写个函数` | `IsCommand=true`（help 接受任意参数）**或** `/help` 不接受参数时 → 提示用法 |
| `/unknown` | `IsCommand=false`（回退 AI） |
| `/ 你好` | `IsCommand=false`（空命令名） |
| `／help`（全角） | `IsCommand=true` |
| ` /clear ` | `IsCommand=true` |

### 11.1.4 `registry.go`

```go
package command

// Registry 命令注册表。
type Registry struct {
    mu       sync.RWMutex
    handlers map[string]Handler
    defs     map[string]Definition
}

func NewRegistry() *Registry {
    return &Registry{handlers: make(map[string]Handler), defs: make(map[string]Definition)}
}

// Register 注册 handler，并用配置覆盖展示层定义。
func (r *Registry) Register(h Handler, override *config.CommandDefinition) error {
    name := h.Name()
    if !validName(name) {
        return fmt.Errorf("command: 非法命令名 %q", name)
    }
    r.mu.Lock()
    defer r.mu.Unlock()
    if _, dup := r.handlers[name]; dup {
        return fmt.Errorf("command: 重复注册 %q", name)
    }
    r.handlers[name] = h
    def := defaultDef(h)                 // 每个 handler 自带默认 usage/description
    if override != nil {
        applyOverride(&def, override)    // 只允许覆盖展示层与 enabled
    }
    r.defs[name] = def
    return nil
}

func (r *Registry) Definitions() map[string]Definition { /* 复制一份返回，避免共享 map */ }
func (r *Registry) Lookup(name string) (Handler, Definition, bool) { /* ... */ }
```

```go
type commandStep struct {
    cfg func() config.Config
    reg *command.Registry
    out *Outbound
    st  Store
}

func (s *commandStep) Name() string { return "command" }

func (s *commandStep) Process(ctx context.Context, t *Turn) (bool, error) {
    if !s.cfg().Commands.Enabled {
        return false, nil
    }
    defs := s.reg.Definitions()
    pr := command.Parse(t.In.Text, defs)
    if !pr.IsCommand {
        return false, nil              // 回退 AI
    }

    // ⚠️ 命令轮标记 filtered：进库但不进上下文（R4）
    t.FilterReason = "command"
    t.Events.Append(ctx, Event{Kind: "command", Message: "命令调用",
        Payload: map[string]any{"name": pr.Name, "args": pr.Args}})

    if pr.Handled {
        t.ReplyText = pr.Hint
        return true, nil
    }

    h, def, ok := s.reg.Lookup(pr.Name)
    if !ok {
        return false, nil
    }
    call := &command.Call{
        Text: t.In.Text, Args: pr.Args, RawArgs: pr.RawArgs,
        Conv: t.In.Conv, Sender: t.In.Sender, ConvID: t.ConvID,
        Def: def, Log: t.Log, Cfg: s.cfg, Store: s.st,
    }
    out, err := h.Run(ctx, call)
    if err != nil {
        return true, fmt.Errorf("命令 /%s 执行失败: %w", pr.Name, err)
    }
    t.ReplyText = out
    return true, nil
}
```

### 11.1.6 命令 handlers 示例（`handlers/help.go`）

```go
package help

type Handler struct {
    reg  *command.Registry   // 为了列出所有命令
    cfg  func() config.Config
}

func New(reg *command.Registry, cfg func() config.Config) *Handler {
    return &Handler{reg: reg, cfg: cfg}
}

func (h *Handler) Name() string   { return "help" }
func (h *Handler) NeedLLM() bool  { return false }   // ✅ 不依赖模型

func (h *Handler) Run(ctx context.Context, c *command.Call) (string, error) {
    defs := h.reg.Definitions()
    names := make([]string, 0, len(defs))
    for n, d := range defs {
        if d.Enabled {
            names = append(names, n)
        }
    }
    sort.Strings(names)

    var b strings.Builder
    b.WriteString("📖 可用命令\n")
    for _, n := range names {
        d := defs[n]
        fmt.Fprintf(&b, "\n/%s —— %s\n用法: %s", n, d.Description, d.Usage)
    }
    return b.String(), nil
}
```

> **注意**：`help.Handler` 依赖 `Registry`，而 `Registry` 又要注册 `help` → 循环。解法：**注册后再注入**，或让 `help` 通过 `Call` 拿到 registry。最简单：给 `Registry` 加一个 `SetDefinitionsProvider`，或者把 registry 传给 `help` 的构造函数时先建 registry 再 `Register(h)`（Go 里这没问题，因为 `help` 持有的是指针，注册发生在之后）。

## 11.2 V2 · 工具调用（AI tools）

### 11.2.1 与命令的区别（别混）

| | 命令（command） | 工具（tool） |
|---|---|---|
| 谁触发 | **用户**打斜杠 | **模型**决定 |
| 入口 | `commandStep`（pipeline 第一步） | `aiStep` 内部的工具循环 |
| 是否需要 LLM | ❌ 不需要 | ✅ 需要（模型发起调用） |
| 落库 | 一轮 `filtered` | 同一轮内的 `assistant(tool_calls)` + `tool(result)` 消息 |
| 例 | `/help`、`/clear` | `query_homework`、`create_scheduled_task` |

### 11.2.2 工具循环（`chat/tools/loop.go`）

```go
// Run 执行「模型 → 工具 → 模型」的循环，直到模型不再要求调用工具或达到步数上限。
func (e *Engine) Run(ctx context.Context, req llm.Request, sink MessageSink) (llm.Response, error) {
    const maxSteps = 5      // ⚠️ 必须有上限，否则模型可能无限循环烧 token

    for step := 0; step < maxSteps; step++ {
        req.Tools = e.Defs()                        // 每步都把工具定义带上
        resp, err := e.client.Complete(ctx, req)
        if err != nil {
            return llm.Response{}, err
        }
        if len(resp.ToolCalls) == 0 {
            return resp, nil                        // 结束：模型给了最终文本
        }

        // ① 把模型的调用意图写进本轮（assistant 消息带 ToolCalls）
        req.Messages = append(req.Messages, llm.Message{
            Role: llm.RoleAssistant, Text: resp.Text, ToolCalls: resp.ToolCalls,
        })
        sink.AppendAssistantToolCalls(ctx, resp.ToolCalls)

        // ② 逐个执行工具
        var results []llm.ToolResult
        for _, tc := range resp.ToolCalls {
            out, err := e.Execute(ctx, tc)
            if err != nil {
                // ⚠️ 工具失败不要中断整轮：把错误作为工具结果回给模型，让它自己解释
                out = fmt.Sprintf("工具执行失败: %v", err)
            }
            results = append(results, llm.ToolResult{CallID: tc.ID, Output: out})
        }
        sink.AppendToolResults(ctx, results)

        // ③ 把结果作为 user/tool 消息回给模型
        req.Messages = append(req.Messages, llm.Message{Role: llm.RoleTool, ToolResults: results})
    }
    return llm.Response{}, fmt.Errorf("工具调用超过 %d 步，已中止", maxSteps)
}
```

**四个关键点**

| 点 | 说明 |
|----|------|
| 步数上限 | 旧 TS 版踩过「无限工具循环」（git log 里有 `工具调用多步循环（带轮数上限）`），这里必须一开始就加 |
| 工具失败不中断 | 把错误文本作为工具结果返回给模型 —— 模型往往能自行补救，而抛错会让用户看到「出错了」 |
| 每步都带 `Tools` | 有些 provider 要求每轮都传工具定义，否则模型会忘记有工具 |
| `sink` 落库 | `assistant(tool_calls)` 和 `tool(result)` 要**写进同一轮**（`seq_in_turn` 递增），这样 V1 的 `RecentTurns` 天然把它们带回上下文（R5 的回报） |

### 11.2.3 出站净化（R17）

```go
// sanitize.go
// Sanitize 把模型输出里可能泄漏的内部协议文本剥掉。
// 旧 TS 版有专门的 tool-call-recovery.ts，因为某些模型不走原生 tool_calls，
// 而是把调用写在文本里（例如 dots_function_call{...}）；并且踩过
// 「工具结果被当作回复发给用户」的坑。
var protocolPatterns = []*regexp.Regexp{
    regexp.MustCompile(`(?s)<\|?tool_calls?\|?>.*?<\|?/?tool_calls?\|?>`),
    regexp.MustCompile(`(?m)^\s*dots_function_call\s*\{.*$`),
    regexp.MustCompile(`(?m)^\s*<function_calls?>.*$`),
    regexp.MustCompile(`(?s)"tool_call_id"\s*:.*?\}`),
}

func Sanitize(text string) string {
    for _, re := range protocolPatterns {
        text = re.ReplaceAllString(text, "")
    }
    text = strings.TrimSpace(text)
    if text == "" {
        return "（模型没有生成有效回复，请再试一次）"
    }
    return text
}
```

**位置**：在 `aiStep` 拿到 `resp.Text` 之后、写进 `t.ReplyText` 之前调用。V1 也可以先放这个函数（空转），但 V2 起必须有测试。

## 11.3 V2.5 · school 能力

### 11.3.1 允许 AI 辅助的边界（重要）

依据 §1.4：school 是「既有 TS 逻辑的翻译」，允许借助 AI。但**边界必须自己守**：

| 可以让 AI 写 | 必须自己定 |
|-------------|-----------|
| HTML 解析函数（`timetable/parse.go`、`electricity/core.go`） | 表结构、接口签名 |
| 请求构造与重试（`cas/http.go`） | 会话互斥的**语义**（同账号并发登录怎么办） |
| 字符串/时间格式化 | 错误分类与用户文案 |
| 单测用例的铺开（给几个样例让它补边界） | 与 `chat`/`store` 的对接方式 |

理由：**翻译逻辑写错只影响功能；接口和表设计错了要返工整个模块。**

### 11.3.3 会话互斥（TS 版的难点，原样需要）

TS 版有 `school/sessions.ts` 处理「同一学号并发登录导致互相踢掉」。Go 版用一把**按用户分片的锁**：

```go
// Sessions 保证同一个身份（学号）在同一时刻只有一个活跃会话。
type Sessions struct {
    mu    sync.Mutex
    byKey map[string]*session       // key = 学号
}

func (s *Sessions) WithSession(ctx context.Context, studentID string, fn func(*session) error) error {
    s.mu.Lock()
    sess, ok := s.byKey[studentID]
    if !ok {
        sess = newSession()
        s.byKey[studentID] = sess
    }
    s.mu.Unlock()

    sess.mu.Lock()                  // 同一身份的串行化
    defer sess.mu.Unlock()

    if !sess.valid() {
        if err := sess.login(ctx); err != nil {
            return fmt.Errorf("school: 登录失败: %w", err)
        }
    }
    err := fn(sess)
    if isCredentialExpired(err) {
        sess.invalidate()           // 让下次调用重新登录
    }
    return err
}
```

> 这里与 `chat` 的串行队列是**两层不同的锁**：`chat` 保证「同一会话的消息按序」，`school.Sessions` 保证「同一学号的校园平台会话唯一」。**不要合并它们**（不同维度）。

### 11.3.4 凭据存储

| 项 | 建议 |
|----|------|
| 存哪 | `school_credentials` 表（V2.5 迁移 `0003`） |
| 加密 | V2.5 先用**明文 + 明确的文档告警**（自用项目），但**列名与接口留出加密位**：`password_enc BLOB`，先存明文并在 `config` 里加 `school.encrypt: false` 开关 |
| 理由 | 真正的加密需要密钥管理（密钥放哪？配置文件里就又是明文）。**先做对接口，别做假安全**。若要加密，用 `crypto/aes` + 从环境变量读的密钥，并把「密钥丢失 = 数据不可恢复」写进文档 |
| 日志 | ⚠️ 任何日志/事件里**绝不打印密码**（`logx.Redact` 覆盖不到动态字段，要在写事件处手动过滤） |

## 11.4 V3 · 定时任务

### 11.4.1 最大的风险：主动消息（先说清）

V1/V2 的所有出站都是**被动回复**（带 `msg_id`）。定时任务不一样：**到点了要主动找用户**。官方平台的限制：

| 限制 | 后果 |
|------|------|
| 主动消息受频控（Bot 维度 + 单关系维度） | 任务多了会被限流 |
| 用户可以关闭「允许主动发送」 | 关闭后**一律发送失败** |
| 群聊主动消息有额外条件 | 群里发不出去 |
| 主动消息会占用配额（例如单关系每天接收上限） | 密集任务不可行 |

**因此 V3 的两个设计决定**：

1. **主动消息失败必须显式记录并可查询**（`events` 里 `kind=schedule_send_failed`），不能静默。用户抱怨「为什么没提醒我」时，你要能一眼看到是频控还是被关闭。
2. **创建任务时要给用户明确预期**：`/cron` 与 AI 工具在创建时就检查「这个频率是否可能触发频控」，超过阈值的任务直接拒绝并说明原因。

### 11.4.2 调度引擎（`internal/schedule/engine.go`）

**不要用「为每个任务起一个 timer」**的写法 —— 任务多了会有成百上千个 timer，且任务编辑时要管理 timer 生命周期。**用统一 ticker + 到期扫描**：

```go
type Engine struct {
    store   Store
    exec    *Executor
    tick    time.Duration      // 默认 30s
    loc     *time.Location
    log     *slog.Logger
}

func (e *Engine) Run(ctx context.Context) error {
    t := time.NewTicker(e.tick)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return nil
        case now := <-t.C:
            if err := e.tickOnce(ctx, now); err != nil {
                e.log.Error("调度轮出错", "error", err)   // 单轮失败不退出引擎
            }
        }
    }
}

func (e *Engine) tickOnce(ctx context.Context, now time.Time) error {
    due, err := e.store.DueTasks(ctx, now, e.tick)      // next_run_at <= now+tick
    if err != nil {
        return err
    }
    for _, task := range due {
        // ⚠️ 幂等：先用 CAS 把 next_run_at 推进，再执行。
        // 若两个 tick 重叠或进程重启后重复扫描，CAS 会失败 → 跳过，避免重复提醒。
        ok, err := e.store.ClaimTask(ctx, task.ID, now)
        if err != nil {
            return err
        }
        if !ok {
            continue
        }
        go e.exec.Run(ctx, task)        // 单个任务失败不影响其他任务
    }
    return nil
}
```

**`ClaimTask` 用 SQL 表达 CAS（关键）**

```sql
UPDATE cron_tasks
SET next_run_at = ?, last_run_at = ?
WHERE id = ? AND next_run_at = ?      -- 乐观锁：只有还是我读到的那一版才更新
```

检查 `RowsAffected() == 1` 即为抢到。这一条能挡住「重复触发」（V3 最容易出的 bug）。

### 11.4.3 崩溃恢复：补跑还是跳过？

进程重启后，`next_run_at` 早已过期的任务怎么办？**必须显式选一个策略并写文档**：

| 策略 | 行为 | 适用 |
|------|------|------|
| **跳过（推荐默认）** | 把 `next_run_at` 直接推进到「下一个未来的时间点」，不补跑 | 「每天 8 点提醒」错过了就没意义，补跑反而在错误时间打扰 |
| 补跑 | 立即执行一次，然后推进 | 里程碑类任务（如一小时后提醒） |

实现：`tickOnce` 里对 `next_run_at < now - grace`（如 10 分钟）的任务走「跳过」分支；对刚过期的正常执行。

**理由**：如果默认补跑，服务重启一次就会收到一串「迟到提醒」，体验很差。

### 11.4.4 Executor：复用 `chat.Outbound`（§8.7 缝 1 的回报）

```go
type Executor struct {
    out    *chat.Outbound          // ← V1 就抽出来的那个类型
    llm    llm.Client
    tools  *tools.Engine           // 可复用 AI 工具
    store  Store
}

func (x *Executor) Run(ctx context.Context, task store.Task) {
    ctx, cancel := context.WithTimeout(ctx, 2*time.Minute)   // 任务级超时
    defer cancel()

    text, err := x.generate(ctx, task)          // 可能是模板，也可能是「让 AI 生成」
    if err != nil {
        x.store.RecordRun(ctx, task.ID, "generate_failed", err.Error())
        return
    }

    // ⚠️ Reply = nil → 主动消息
    res := x.out.SendText(ctx, task.Conv, nil, text, task.ChatCfg)
    if res.Sent == 0 {
        x.store.RecordRun(ctx, task.ID, "send_failed", res.Err.Error())
        x.events.Append(ctx, Event{Kind: "schedule_send_failed", Level: "warn",
            Message: "主动消息发送失败（可能被频控或用户关闭了主动发送）",
            Payload: map[string]any{"task_id": task.ID, "error": res.Err.Error()}})
        return
    }
    x.store.RecordRun(ctx, task.ID, "ok", "")
}
```

### 11.4.5 时间解析

TS 版有 `cron/parser.ts`（658 行）与 `cron/parser.test.ts`（508 行）—— **这是可以放心直接搬的部分**（§7.7）。

Go 版建议分层：

| 输入形式 | 处理方式 | 依赖 |
|---------|---------|------|
| `每天 8:00`、`每周一 9:30`、`每小时` | 自己写解析（正则 + 结构化） | 无 |
| `*/5 * * * *`（真 cron 表达式） | 引 `github.com/robfig/cron/v3` 的 `Parse` **只用于算下一次时间**，不用它的调度器 | 一个依赖 |
| `明天早上提醒我交作业` | 交给 **AI 工具** `create_scheduled_task`，由模型解析成结构化时间 | LLM |

**建议**：V3 先支持「固定格式 + cron 表达式」两种，自然语言留给 AI 工具路径（这样解析失败的锅由模型背，而不用写一个自然语言时间解析器）。
