# 第一部分 · 范围与迭代

## 1.1 项目定位

| 维度 | 定位 |
|------|------|
| 用途 | ① 作者在校期间自用；② 供学弟学习 Go + 机器人开发的参考项目 |
| 学习属性 | **手写为主**，AI 只用于答疑与局部难点（V2.5 的 school 模块允许借助 AI，见 §1.4） |
| 前端 | **始终不做页面**，能力全部通过 admin HTTP API 暴露；页面优先级最低 |
| 部署 | 单二进制 + 一个配置文件 + 一个 data 目录 |

「学习属性」不是口号，它有三个硬性约束，会贯穿所有设计决策：

1. **可测试**：不许出现「无全局单例就测不了」的结构（→ 排除旧方案的 `sync.Once` + `panic` 单例）
2. **可读**：目录按业务能力切，不按技术层切（→ 方案 B，见 02）
3. **可替换**：换平台/换模型协议只加适配器，不动业务（→ 端口/适配器）

## 1.2 迭代总览

| 迭代 | 主题 | 一句话验收 |
|------|------|-----------|
| **V1** | 单链路跑通 + 可运维 | 在 QQ 里私聊机器人，收到 AI 回复；通过 curl 能看日志、改配置、重载、重连、重启 |
| **V2** | 命令框架 | 不启用 AI 的情况下，`/help` `/prompt` `/clear` 仍然可用 |

### 明确的「永不进入本项目」项

| 项 | 原因 |
|----|------|
| 语音/TTS 回复 | 用户明确取消（官方 Bot 发语音需先上传富媒体，机制与 OneBot 完全不同，收益低） |
| 管理前端页面 | 用户明确降级，永远 API-only |
| OneBot 11 / NapCat 适配器 | 用户已明确改走官方链路；但 `platform.Provider` 接口保留这种可能性 |

## 1.3 V1 范围（本次唯一要交付的迭代）

### ✅ 包含

| # | 能力 | 说明 |
|---|------|------|
| 1 | 进程骨架 | `cmd/botd` 组合根、配置加载、日志初始化、优雅关闭、SIGTERM/SIGINT 处理 |
| 2 | QQ 官方 Bot **单聊**收发 | botgo WS 接收 `C2C_MESSAGE_CREATE`；`PostC2CMessage` 被动回复 |
| 3 | AI 调用 | 一次请求-响应（无工具、无流式），带重试与超时 |
| 4 | **三种模型协议适配器** | OpenAI chat / OpenAI responses / Anthropic messages，各一个实现 |
| 5 | 上下文拼接 | 取该会话**最近 10 轮有效对话**（定义见 §4.3） |
| 6 | 长回复分段发送 | 按长度切分，受**被动回复次数上限**约束（见 R1） |
| 7 | 入站消息幂等去重 | 同一 `msg_id` 重复推送只处理一次 |
| 8 | 同一会话串行处理 | 同一会话的消息按顺序处理，不会并发污染上下文 |
| 9 | SQLite 持久化 | 4 张表：`conversations` / `turns` / `messages` / `events`；启动时自动迁移；只建 V1 需要的表 |
| 10 | 配置 | `config.yaml` + 环境变量覆盖；字段级热重载 |
| 11 | 日志双轨 | 文本日志→文件（按天/大小切）；业务事件→DB（供 API 查询） |
| 12 | admin API | `health` / `config (GET,PUT)` / `config/reload` / `bot/reconnect` / `system/restart` / `logs` |
| 13 | 单测 | 上下文裁剪、有效性过滤、分段、会话 key、配置合并、迁移推进 —— 用 mock Provider + mock LLM 跑通 chat 全链路 |

### ❌ V1 明确不含

| 项 | 归属 |
|----|------|
| 命令框架（任何斜杠命令） | V2 |
| AI 工具调用（tool calling） | V2 起。**但接口与数据模型必须 V1 就留好**（见 §3.3、R7） |
| 群聊 | 以后。**但会话身份模型必须 V1 就是 group-ready**（见 §3.1） |
| 长期记忆（用户画像/摘要/相关记忆） | 以后 |
| 定时任务引擎、cron 相关表 | V3 |
| school（CAS/课表/作业/电费） | V2.5 |
| 语音/TTS | 永不 |
| Webhook 接收链路 | 未排期，但接口预留（见 §3.1.4） |
| 多 Bot 实例 | 不排期，但 DB 表带 `app_id` 列（见 §4.1） |
| 前端页面 | 永不 |

### 非文本消息如何处理（V1 必须明确）

官方单聊事件可能带 `attachments`（图片/语音/文件）。V1 **只处理文本**，策略：

| 收到 | 行为 |
|------|------|
| 纯文本 | 正常走 AI |
| 仅非文本（图片/语音/文件） | 回一条固定提示（「目前只支持文字消息」），**不写入上下文**，不调用模型 |
| 文本 + 非文本混合 | 只取文本部分走 AI，并在日志中记录被忽略的附件 |

理由：不明确这一点，用户发张图会得到模型对空内容的编造回复，且污染上下文。

## 1.5 V1 验收标准

### 功能验收（黑盒）

1. 在 QQ 私聊给机器人发「你好」，收到 AI 的文本回复
2. 连发 3 条不同问题，回复内容与顺序**一一对应**（验证同会话串行 + 上下文）
3. 问「我上一条说了什么」，回复能正确引用，验证上下文拼接生效
4. 发一条会触发超长回复的问题，回复被正确拆成多条且无重复、无截断错乱
5. 发一张图片，收到「只支持文字」提示，且 `GET /admin/logs` 中没有产生 AI 调用事件
6. 断开网络 10 秒后恢复，机器人自动重连并继续正常响应（验证 WS 重连）
7. 手动重放同一条事件（或依赖官方重复推送），只回复一次（验证幂等）

### 运维验收（curl）

```bash
curl -H "Authorization: Bearer $TOKEN" localhost:8081/admin/health         # 200，含 bot/llm/db 子状态
curl -H "Authorization: Bearer $TOKEN" localhost:8081/admin/config          # 200，密钥字段已脱敏
curl -X POST -H "Authorization: Bearer $TOKEN" localhost:8081/admin/config/reload   # 改 model 后无需重启生效
curl -X POST -H "Authorization: Bearer $TOKEN" localhost:8081/admin/bot/reconnect   # WS 断开重连
curl -X POST -H "Authorization: Bearer $TOKEN" localhost:8081/admin/system/restart  # PID 不变，配置重读
curl "localhost:8081/admin/logs?kind=llm_call&limit=20"                     # 分页查业务事件
```

### 质量验收

- `go build ./...`、`go vet ./...`、`go test ./...` 全绿
- chat 全链路单测：**不连接真实 QQ、不调用真实模型**即可跑通（用 mock Provider + mock LLM）
- `CGO_ENABLED=0 GOOS=linux go build ./cmd/botd` 能产出可运行的 Linux 二进制（验证纯 Go SQLite 的选型价值）

## 8.1 「完成度」的三级刻度

每一轮迭代里，每个包都要明确自己处于哪一级。**不要所有包都做到 L3** —— 那是过度设计。

| 级别 | 名字 | 含义 | 判定标准 |
|------|------|------|----------|
| **L1** | 能跑 | 有一个正确实现，能被真实调用 | 手动验证路径通 |
| **L2** | 能测 | 有单测，逻辑边界被覆盖；依赖通过接口注入，可替换为假实现 | `go test ./...` 全绿，且测试**不连外部服务** |
| **L3** | 能运维 | 有可观测性（日志/事件/health 信号）+ 错误可分类 + 有降级路径 | 出故障时能通过 `/admin/health` + `events` 定位 |

**默认策略**：核心业务（`chat`）做到 L3；适配器（`platform/provider/*`、`llm/provider/*`）做 L2（真实调用无法在单测里验证，靠 `httptest` + 手动冒烟）；基础设施（`config`、`store`、`logx`）做 L2；`admin` 做 L2。

## 8.3 各迭代「每个包做到什么程度」

### V1

| 包 | 深度 | 具体标准 | 不做 |
|----|------|----------|------|
| `cmd/botd` | L2 | 启动顺序正确、优雅关闭清单全走完、SIGTERM 有效、`-migrate-status` 可用 | 不做子命令框架 |
| `config` | L2 | YAML + `${VAR}` 替换 + env 覆盖 + `Validate()` + `Diff()` 三档分类 | 不做配置中心、不做多文件 merge |
| `logx` | L2 | 双写（文件+控制台）、轮转、`Redact`、trace_id 字段 | 不做采样、不做远程日志 |
| `store` | L2 | 4 张表 + 迁移 + 查询方法；`t.TempDir()` 起的单测可跑迁移 | 不做 ORM、不做读连接池分离 |
| `platform`（端口） | L2 | 接口 + mock 实现；mock 能注入任意事件 | 不做 webhook（只留接口） |
| `platform/qqbot` | **L1+ 冒烟** | 能真实收发、能重连、botgo 日志接管、次数耗尽错误映射 | 单测只测 `inbound`/`outbound` 的**纯转换函数**（不测网络） |
| `llm`（端口） | L2 | 中性模型 + retry + 错误分类 | 不做流式、不做缓存 |
| `llm/provider/*` | L2 | 三个适配器 + `httptest` 测试（含工具调用响应的解析） | 不做流式 SSE |
| `chat` | **L3** | 幂等（含 R15 恢复）、同会话串行、上下文按轮裁剪、分段受被动次数限制、错误文案分类、事件全记 | 不做限流、不做优先级队列 |
| `admin` | L2 | 12 个端点 + Bearer 鉴权 + 脱敏 + 游标分页 | 不做 SSE、不做页面 |

### V2

| 包 | 深度 | 标准 |
|----|------|------|
| `chat/command` | L3 | 解析歧义规则（R18）单测齐全；命令轮 `status=filtered`；不依赖 LLM（关掉 `llm.enabled` 仍可用） |
| `chat/tools` | L2 | tool loop 有轮数上限（防死循环）；出站净化有测试 |
| `store/user.go` | L2 | 从 `turns` 回填历史 openid（一次性迁移脚本或启动时惰性创建） |
| `llm` | **零改动** | 若这里需要改，说明 V1 的中性模型设计失败 |

### V2.5

| 包 | 深度 | 标准 |
|----|------|------|
| `school/cas` | L1 | 真实登录能过；会话互斥（同账号并发登录）有锁；换绑学号逻辑正确 |

| 包 | 深度 | 标准 |
|----|------|------|
| `schedule/parser` | L2 | 纯函数，可直接搬 TS 的 `cron/parser.ts` 测试用例 |

## 8.7 「缝清单」——V1 必须预留的 9 个前向兼容点

这是本文档最有价值的一张表：**在 V1 就把这些「缝」留出来，后续迭代就不用返工**。每条都注明「如果不留会怎样」。

| # | 缝 | V1 怎么留 | 留给谁 | 不留的后果 |
|---|----|-----------|--------|-----------|
| 1 | `chat/outbound.go` 独立成可复用类型 | 把「分段 + 发送 + 记事件」放进 `Outbound`（持有 `platform.Provider`），`chat.Service` 调它 | V2.5（作业长列表）、V3（定时任务主动消息） | V3 要在 `chat.Service` 里挖出发送逻辑，牵着 pipeline 一起改 |
| 2 | `Pipeline.Step` 接口 | V1 的 `[]Step{aiStep}` 就是列表，不是硬编码调用 | V2（命令步骤插到最前） | V2 要重构 `Service` 的控制流 |
| 3 | `turns.status` 含 `processing` / `filtered` | 建表时就写进注释与 CHECK 取值 | V2（命令轮 = filtered）、R15（崩溃恢复） | 加状态要改表 + 改所有判定 |
| 4 | `llm.Message{Text, ToolCalls, ToolResults}` + `Request.System` | 字段齐全，工具相关的 V1 恒空 | V2（工具调用） | 三个协议适配器全返工（R7） |
| 5 | `ConversationKey.Scene` + `conversations.scene` 列 | V1 只写 `c2c`，但类型与列都在 | 以后（群聊） | 要改接口签名 + 加列 + 回填 |
| 6 | `OutgoingMessage.Reply` 可为 nil | `Reply *ReplyRef`，nil = 主动消息 | V3（定时任务） | 类型设计成必填后，主动消息无从表达 |
| 7 | `platform.WebhookReceiver` 接口 | 只写接口定义，不写实现 | WS 下线时（R22） | 接收方式绑定 WS，切换要动 `Provider` 接口 |
| 8 | 每张业务表带 `app_id` 列 | V1 就加上（单 Bot 时值唯一） | 多 Bot / 沙箱正式共存 | 加列 + 回填 + 改所有索引与唯一约束 |
| 9 | `users.union_openid` 列（V2 建表时） | V2 的迁移里就带上 | V2.5（学号打通私聊/群聊身份，R8） | 身份打通时要改表 + 改查询 |

> 判断方法：**任何「以后可能会多一种类型/多一个来源」的地方，V1 就用枚举 + 可空字段表达出来，而不是用布尔值或硬编码。** 这条原则能挡掉 80% 的返工。

## 8.8 「不要提前做」清单（防止自己过度设计）

| 想法 | 为什么现在不做 | 什么时候做 |
|------|---------------|-----------|
| 「先把 cron 表建好」 | 预建的表 99% 与最终设计不一致（§4.8） | V3 |
| 「先加上限流，以后省事」 | 同会话串行队列已天然限速；加限流要调参、要测试 | 真被刷时 |
| 「抽象一个通用事件总线」 | V1 只有一个事件来源，总线是纯粹的多余层 | 出现第二个来源且需要交叉时 |
| 「给 `chat` 加优先级队列」 | 只有一条链路，优先级无处体现 | 命令与 AI 需要抢占时（V2 再说） |
| 「支持配置热切换 provider」 | 换 provider 需重启（§5.2），这是刻意的 | 永不（成本远大于收益） |
| 「写个通用的 Repository 泛型」 | Go 泛型 + SQL 的组合会让代码更难读 | 永不（手写 SQL 更好学） |
| 「给每个包都做 interface」 | 接口在**使用方**定义，只为「需要替换」而存在 | 出现第二个实现时 |
| 「先做前端页面」 | 用户已定永不 | 永不 |
