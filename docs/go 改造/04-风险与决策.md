## 6.1 风险清单

### R1 · 分段发送撞上「被动回复次数上限」🔴 V1 必踩

| 项 | 内容 |
|----|------|
| 症状 | 长回复第 5 段开始静默失败；用户只收到前半截 |
| 根因 | 官方规定：单聊 60 分钟内一条入站消息**最多被动回复 4 次**，群聊 5 分钟 5 次。而「把长回复切成 6 段」是旧 TS 版的常规行为（OneBot 没有这个限制） |
| 对策 | ① `chat.max_reply_segments` 默认 **3**（留 1 次余量给错误提示）；② 超出直接合并/截断；③ 适配器把「次数耗尽」错误码映射为 `platform.ErrReplyQuotaExhausted`，`chat` 停止后续段并记 `outbound_error` |
| 验证 | 构造一条超长回复，`GET /admin/logs?kind=outbound` 中段数 ≤ 3，且无 `outbound_error` |
| 归属 | **V1** |

### R2 · 入站消息重复推送导致重复回复 🔴 V1 必踩

| 项 | 内容 |
|----|------|
| 症状 | 用户一句话，机器人回两遍；消耗两次被动回复配额 |
| 根因 | 官方文档明确：**相同 `msg_id` 可能重复推送**（WS 重连/resume 会加剧） |
| 对策 | `turns` 表上的 `UNIQUE(conversation_id, inbound_msg_id)` 做**持久化幂等**；内存 LRU 只作快路径。冲突时跳过并记 `inbound_duplicate` |
| 验证 | 单测直接对同一 `MsgID` 调两次 pipeline；集成测试用 `/admin/debug/inject` 连发同一 `msg_id` |
| 归属 | **V1** |

### R3 · 同一会话并发处理导致上下文污染 🔴 V1 必踩

| 项 | 内容 |
|----|------|
| 症状 | 用户连发 3 条，回复与问题错位；上下文中 user/assistant 顺序颠倒；两条回复都读到了「对方的」上下文 |
| 根因 | 每个事件起一个 goroutine 是最自然的写法（`for ev := range events { go handle(ev) }`），但同一会话的两次处理会并发读写同一段上下文 |
| 对策 | `chat/dispatcher.go`：**按 `ConversationKey` 分片的串行队列**（N 个 worker goroutine，每个持一个 channel，`hash(key) % N` 决定归属）。同会话天然串行，不同会话仍然并行；顺带起到天然限速作用（这也是 V1 不引限流库的理由，见 D-4） |
| 验证 | 单测：向同一会话连投 3 条，断言处理顺序与完成顺序一致；并发投 2 个会话，断言两者可并行 |
| 归属 | **V1** |

### R4 · 命令消息污染 AI 上下文 🟠 V2 会踩，但 V1 就要留好位置

| 项 | 内容 |
|----|------|
| 症状 | 用户打了 `/help`、`/clear`、`/prompt xxx`，之后模型在对话里「记得」这些命令文本，行为诡异 |
| 根因 | 命令和普通消息走同一条 pipeline；若命令也建 `ok` 轮，就会被 `RecentTurns` 取进上下文 |
| 对策 | 命令轮一律 `status='filtered'`（进 DB 供审计，**不进上下文**）；`chat.Pipeline` 的步骤链里 `commandStep` 排在 `aiStep` 之前，命中即 `handled=true` |
| 验证 | V2 单测：发 `/help` 后断言 `turns.status='filtered'` 且下一次请求的 Messages 里不含 `/help` |
| 归属 | V1 设计预留（`status` 枚举、Step 接口），**V2 落地** |

### R5 · 「轮」的算法在 V2 加工具调用后返工 🟠 设计债

| 项 | 内容 |
|----|------|
| 症状 | V2 加了 tool calling 后，上下文里出现「只有工具调用没有最终回答」或「有工具结果没有调用」的残片，模型开始胡言乱语 |
| 根因 | 若「最近 10 轮」按 `messages` 的行数取（如 `LIMIT 20`），一轮产生的 4 行（user / assistant(tool_calls) / tool(result) / assistant(text)）会被截断在中间 |
| 对策 | 独立 `turns` 表：先按轮取 10 个 `id`，再取这些轮的**全部**消息。V2 加工具后**算法一行不改** |
| 验证 | V1 单测就写「一轮含 4 条消息时，窗口裁剪不产生残轮」（用假数据插入 tool 角色） |
| 归属 | **V1**（这是 V1 里杠杆最高的一个设计决策） |

### R6 · 沙箱与正式是两个 AppID，数据会混库 🟠 V1 会踩

| 项 | 内容 |
|----|------|
| 症状 | 沙箱测试时的对话出现在正式环境的上下文里；换 AppID 后所有历史数据「指向不存在的用户」 |
| 根因 | 官方规则：**同一用户/群在不同 AppID 下的 openid 完全不同**。开发时通常同时用沙箱和正式 |
| 对策 | ① 所有业务表带 `app_id` 列，`ConversationKey` 含 `AppID`；② `bot.qqbot.app_id` / `sandbox` 属「必须重启」档（§5.2），reload 时明确拒绝并提示 |
| 验证 | `GET /admin/conversations` 能按 app_id 过滤；沙箱/正式数据互不可见 |
| 归属 | **V1** |

### R7 · 三种模型协议的差异在 V2 加工具时集中爆发 🟠 设计债

| 项 | 内容 |
|----|------|
| 症状 | V2 加工具后，Anthropic 适配器要重写大半（`tool_use`/`tool_result` 是 content block，与 OpenAI 的 `role:tool` 机制完全不同）；Responses 的 `instructions` 与 Chat 的 `messages[0]` 也不一样 |
| 根因 | V1 无工具，容易只做「文本进、文本出」的薄封装，把协议差异的责任推给上层 |
| 对策 | V1 就把**中性模型**（`llm.Message{Text, ToolCalls, ToolResults}` + `Request.System` 顶层字段）和三条完整转换路径写完，即使没有工具可传 |
| 验证 | 每个适配器都写一个 `httptest.Server` 测试：喂**带工具调用的固定响应**，断言解析成中性模型正确（V1 就能做，不需要真的有工具） |
| 归属 | **V1** |

### R8 · `user_openid` 与 `member_openid` 是「两个不同的人」🟡 以后会踩

| 项 | 内容 |
|----|------|
| 症状 | 同一个同学在私聊和群里被当成两个用户：私聊设置的 `/prompt` 在群里不生效；记忆/画像分裂 |
| 根因 | 官方规定：私聊标识是 `user_openid`，群里标识是 `member_openid`，**即使同一个人、同一个 AppID 也不同**。官方预留的 `union_openid` / `union_user_account` 目前语义有限 |
| 对策 | ① V1 表结构就把「会话」和「发送者」分开（`conversations.scene_openid` vs `turns.sender_openid`）；② V2 的 `users` 表预留 `union_openid` 列；③ 真正的打通留到 V2.5（学号绑定是天然的跨场景身份锚点 —— 用学号把私聊和群里的 openid 系在一起） |
| 验证 | V2.5 设计时确认「用学号作为 identity anchor」是否覆盖所有场景 |
| 归属 | V1 表结构预留，V2.5 落地 |

### R9 · 密钥进 git / 进日志 🔴 V1 必做（低成本高收益）

| 项 | 内容 |
|----|------|
| 症状 | AppSecret、LLM API Key 出现在公开仓库或日志文件里 |
| 根因 | 配置模板里直接写真实密钥；适配器在 debug 级别打印完整请求头；错误响应体带 key 片段 |
| 对策 | `.gitignore` 排除 `config.yaml`；只提交 `config.example.yaml` 且值写成 `${QQBOT_APP_SECRET}`；`logx.Redact` 强制过一遍请求头；admin API 返回脱敏 |
| 验证 | `git grep -i "app_secret\|api_key" -- '*.yaml'` 只应命中占位符 |
| 归属 | **V1** |

### R10 · admin API 暴露面 🔴 V1 必做

| 项 | 内容 |
|----|------|
| 症状 | 有人扫到 8081 端口就能重启你的服务、改你的模型配置、读你的全部聊天记录 |
| 根因 | 旧 TS 版的默认 token 是硬编码的 `napcat-admin-token`；且默认监听 `0.0.0.0` |
| 对策 | token 空 → **拒绝启动**；默认 `127.0.0.1`；`subtle.ConstantTimeCompare` 比较；改监听地址时打 warn；`/admin/logs` 里的 payload 是聊天原文，属于隐私数据 |
| 验证 | 无 token 请求返回 401；`netstat` 确认默认只绑 127.0.0.1 |
| 归属 | **V1** |

### R11 · `go run` 场景下自我重启会把自己搞死 🔴 V1 必须处理

| 项 | 内容 |
|----|------|
| 症状 | 调 `POST /admin/system/restart` 后服务再也没起来（或起来的是旧代码） |
| 根因 | `go run` 编译到 `/tmp/go-buildXXXX/b001/exe/...`，进程被回收后该目录会被删除；`syscall.Exec` 指向一个不存在/过期的文件 |
| 对策 | 启动时用 `os.Executable()` 判断路径是否在临时目录/含 `go-build`，命中则 `restart` 端点直接返回 409 并提示用 `make run` 或已编译二进制；同时 `syscall.Exec` 失败时**不退出**，回滚为 500 + 错误事件 |
| 验证 | `go run ./cmd/botd` 下调用 restart → 期望 409；`./bin/botd` 下调用 → PID 不变且配置重读 |
| 归属 | **V1** |

### R12 · botgo 的日志与重连行为 🟠 V1 会踩

| 项 | 内容 |
|----|------|
| 症状 A | 日志里出现两套格式，botgo 的日志不进文件、也不带 trace_id |
| 症状 B | 一次消息被处理两次 |
| 根因 A | botgo 自带 `log` 包，未接管 |
| 根因 B | WS 断线自动 resume；若把 `event.RegisterHandlers` 放在每次重连回调里，handler 会被重复注册 |
| 对策 | ① 用 botgo 的自定义 logger 接口接到 `logx`（参考其 `examples/custom-logger`）；② handler 只在 `Start` 注册一次；③ 重连只重建 session，不重建 handler |
| 验证 | 手动断开网络 10s，恢复后发一条消息，`events` 表中 `inbound` 只出现一次 |
| 归属 | **V1** |

### R13 · 非文本消息让模型编造回答 🟠 V1 会踩

| 项 | 内容 |
|----|------|
| 症状 | 用户发一张图，机器人回一段与图片毫无关系的话（因为它只看到空文本 + 一些附件元数据） |
| 根因 | 官方单聊事件可能带 `attachments`，而 V1 只处理文本 |
| 对策 | 见 §1.3 的处理表：仅非文本 → 固定提示 + `status='filtered'`，不调模型；文本+非文本 → 只取文本并记日志 |
| 验证 | 验收标准第 5 条（发图片后 `events` 里无 `llm_call`） |
| 归属 | **V1** |

### R14 · 上下文超过模型上下文长度 🟠 后期会踩

| 项 | 内容 |
|----|------|
| 症状 | 某些对话突然开始报错（`ErrContextTooLong`），且此后该会话一直报错 —— 因为历史里有一条超长消息，永远处于窗口内 |
| 根因 | 「最近 10 轮」是按**轮数**裁剪的，不是按 **token 数**。若某一轮用户贴了 8000 字，10 轮就爆上下文 |
| 对策 | ① 入口处限制单条入站文本长度（如 4000 字符，超出截断并记事件）；② `ErrContextTooLong` 时**降级重试**：把窗口从 10 轮逐次减半（10 → 5 → 2 → 0）再调一次；③ 全失败才向用户报错。这条要在 V1 就定下策略（哪怕只实现「限长 + 报错+可读文案」），否则用户会看到「这个会话坏了但新建会话就好」的诡异现象 |
| 验证 | 单测：注入 3 轮各 5000 字，断言窗口降级重试后成功 |
| 归属 | 策略 V1 定，完整降级实现 V1 末或 V2 |

### R15 · 幂等约束与崩溃恢复的冲突 🟠 设计细节，容易写错

| 项 | 内容 |
|----|------|
| 症状 | 进程崩溃在「已建轮、未回复」之间；WS resume 后平台**重推**同一条消息 → 幂等约束命中 → 跳过 → **这条消息永远没人回** |
| 根因 | 幂等只看「是否见过」，没看「上一轮是否真的完成了」 |
| 对策 | `turns.status` 的中间态 `processing`（见 §4.2）+ `finished_at IS NULL`；重复推送时的判定规则：
① 已有轮且 `finished_at IS NOT NULL` → 真重复，跳过
② 已有轮但 `finished_at IS NULL` 且 `started_at` 距今 < 阈值（如 5 分钟）→ 视为「正在处理中」，跳过（同会话串行队列正在跑）
③ 已有轮但 `finished_at IS NULL` 且已超阈值（或启动时扫描到残轮）→ **接管重试**：复用该轮，重新走 AI 与发送 |
| 验证 | 单测：手工插入一条 `finished_at=NULL` 的轮，再投同一 `msg_id`，断言走了「接管重试」分支 |
| 接口依据 | `BeginTurn` 返回 `TurnRef{IsNew}` 强制在调用点处理这个分支（§3.4.3） |
| 归属 | **V1**（这是本清单里最容易写错的一条） |

### R16 · 分段发送中途失败 🟡 体验问题

| 项 | 内容 |
|----|------|
| 症状 | 3 段回复，第 1 段成功、第 2 段失败 → 用户看到半截话，且轮被标记 `failed`（下一轮上下文里没有这轮） |
| 对策 | 每段成功都写 `outbound` 事件（含「第 i/n 段」），失败时写 `outbound_error`；`failed` 判定改为「**第 1 段**失败才算 failed」，只要发出去过内容就记 `ok`（因为用户已经看到部分内容，模型也应该知道它说过什么） |
| 验证 | 用 mock provider 让第 2 段强制失败，断言轮状态与事件序列 |
| 归属 | **V1** |

### R17 · 模型输出泄漏内部协议文本 🟡 V2 会重现

| 项 | 内容 |
|----|------|
| 症状 | 用户收到 `dots_function_call{"name":...}` 之类的原始工具协议文本 |
| 根因 | 某些模型不走原生 tool_calls，而是把调用写在文本里；旧 TS 版专门写了 `ai/tool-call-recovery.ts` 处理这种模型，并且踩过「工具结果回显给用户」的坑 |
| 对策 | V2 起在 `chat` 出站前加一个**净化步骤**（从文本中剥离工具调用片段、剥离工具结果回显）。V1 无工具，暂不需要，但 `chat.Pipeline` 的 Step 机制就是为它留的位置 |
| 验证 | V2 起：用「文本式工具调用」的模型跑一遍，断言用户看不到协议文本 |
| 归属 | V2（V1 只需知道它一定会来） |

### R18 · 命令前缀与普通文本的歧义 🟡 V2 设计点

| 项 | 内容 |
|----|------|
| 症状 | 用户正常打「/help me 写个函数」被当成命令；或用户打了 `/clear` 但带全角斜杠 `/` 或前导空格导致没被识别 |
| 对策 | ① 只有当首个 token **完全等于**已知命令名（且该命令 enabled）才当命令，否则整条走 AI；② 解析前先做：去首尾空白、把全角 `／` 归一化为 `/`；③ 解析失败（命令名不存在）时**回退到 AI** 而不是回「未知命令」 |
| 验证 | V2 单测：`/help` → 命令；`/help me` → 走 AI；` /clear` → 命令；`/unknown` → 走 AI |
| 归属 | V2 |

### R19 · `events` 表无限增长 🟡 低成本

| 项 | 内容 |
|----|------|
| 对策 | 按 `log.event_retention_days`（默认 14）保留；启动清理一次 + 每 24h 清理；payload 单条截断到 `event_payload_max_kb` |
| 归属 | V1（最小实现即可） |

### R20 · 时间前缀时区错位 🟢 低成本

| 项 | 内容 |
|----|------|
| 症状 | 服务器 UTC，用户 UTC+8，历史消息前缀显示「[09-25 18:00]」而用户实际是 09-26 02:00 |
| 对策 | 配置 `chat.timezone`，用 `time.LoadLocation` 显式加载（**不要用 `time.Local`**）；DB 只存 Unix 毫秒 |
| 归属 | V1 |

### R21 · 优雅关闭等太久 🟢 低成本

| 项 | 内容 |
|----|------|
| 症状 | 重启时卡住数十秒；或反过来等太久导致被动回复窗口过期，回复白等 |
| 对策 | `shutdown_grace` 默认 15s，超时放弃并 warn；被中断的轮留 `finished_at=NULL`（也是 R15 的输入） |
| 归属 | V1 |

### R22 · WS 链路未来下线 🟡 战略风险

| 项 | 内容 |
|----|------|
| 事实 | 官方已公告 WS 事件链路将逐步下线、后续不再维护；新链路是 **webhook**（要求 HTTPS 回调 + `plain_token`/`event_ts` 签名验签，允许端口 80/443/8080/8443） |
| 现状 | 你已用 WS（botgo）测通，短期可用 |
| 对策 | ① `platform.Provider` 端口不变；② 预留 `platform.WebhookReceiver` 接口（§3.1.4），未来 webhook 适配器与 admin HTTP **共用端口**；③ 配置里 `bot.provider` 是切换点（未来加 `qqbot-webhook`） |
| 缓解代价 | V1 只需「不把 WS 特有假设写进 `chat`」（如：不要把「长连接存活」当作系统健康的唯一标志） |
| 归属 | V1 预留接口，未排期实现 |

### R23 · 正式环境的 IP 白名单 🟡 上线前必踩

| 项 | 内容 |
|----|------|
| 症状 | 本地/新服务器调用 OpenAPI 直接被拒（沙箱不受限，正式环境限制） |
| 对策 | 记录到部署文档；`/admin/health` 里把「token 获取成功」作为一项显式健康信号，让这个问题在健康检查里立刻可见，而不是等到用户发消息才发现 |
| 归属 | V1（健康信号）+ V3（部署文档） |

## 6.3 决策记录（已定，附理由，避免以后反复讨论）

| # | 决策 | 理由 |
|---|------|------|
| D-1 | 架构用「端口/适配器 + 组合根」，不用技术分层 + 全局单例 | 可测试 + 可替换 + 学弟可读（§2.6） |
| D-2 | 工厂/策略用**显式 `switch`**，不用 `init()` 注册表 | v1 只有 1 个 bot + 3 个 llm 实现，注册表是过度设计（§2.4） |
| D-3 | 不引 Web 框架 / ORM / DI 库 / 配置库 / 日志库 | 12 个端点、1 个数据源；每多一层都是学弟的阅读成本（§5.9） |
| D-4 | V1 **不引限流库**，靠同会话串行队列天然限速 | YAGNI；真需要时加在 `chat` 层，不影响其它包（R3） |
| D-5 | 日志轮转**用 lumberjack**，不手写 | 轮转的边界条件是 bug 温床，学习收益低；`logx` 是门面，将来可换（§5.7） |
| D-6 | 幂等用 `turns` 表的 UNIQUE 约束，不建独立去重表 | 少一张表 + 天然持久化 + 与轮的生命周期一致（§4.2） |
| D-7 | 分段默认 **3** 段 | 被动回复上限 4，留 1 次余量（R1） |
| D-8 | 模型重试**最多 3 次**（1s→2s→4s），不是旧方案的 5 次 | 5 次最长 31s+，单聊体验上用户已放弃（§3.3.4） |
| D-9 | 不预建未来迭代的表 | 预建的表 99% 与最终设计不一致，反而更贵（§4.8） |
| D-10 | V1 不含任何命令 | 用户明确要求；且命令框架值得单独一个迭代认真做（§1.2） |
| D-11 | V1 不含群聊，但会话身份模型 group-ready | 接口改一次比表改一次便宜得多（§1.3） |
| D-12 | 三个模型协议适配器 **V1 全部写完** | 否则 V2 加工具时三个都要返工（R7） |
| D-13 | DB 用 `modernc.org/sqlite`（纯 Go）+ `SetMaxOpenConns(1)` | 交叉编译友好 + 从根上消除 SQLITE_BUSY（§4.6） |
| D-14 | 时间统一存 Unix 毫秒 | 显示层负责时区，DB 只存绝对时刻（§4.6） |

## 6.4 明确「不做」的东西（反 YAGNI，写下来挡未来的自己）

| 不做 | 什么时候才该做 |
|------|---------------|
| 多 Bot 实例 / 多租户 | 真有第二个机器人时（表已带 `app_id`，成本低） |

| 流式响应（SSE）给 QQ | 官方 Bot 不支持流式消息；只能靠分段模拟 |

| 语音/TTS | 永远（用户已取消） |
| gRPC / GraphQL admin | 永远，HTTP+JSON 足够 |
| 配置中心 / 热更新的复杂合并策略 | 永远，YAML 文件 + reload 足够 |

## 2.6 与旧 `GO_REFACTOR_PLAN.md` 的差异（它被本方案取代）

| # | 旧方案 | 本方案 | 原因 |
|---|--------|--------|------|
| 1 | `internal/{bot,ai,config,db,handler,logger,server,domain}` 技术分层 | 端口/适配器 + 按能力切分 | 旧方案的 `handler` 会成为杂物间；`domain` 会成为「说不清该放哪就放这」的抽屉 |
| 2 | 全局单例 + `sync.Once` + `panic`（`ai.GetClient()`、`db.GetDB()`） | 组合根显式 new + 接口注入 | 单例让任何单测都要处理全局状态；`panic` 让启动失败无法优雅报错 |
| 3 | `config.Load()` 内部直接调用 `ai.GetClient().UpdateConfig()` | config 只做「加载+变更分类」，由组合根/订阅者决定谁响应 | 旧写法是循环依赖的种子（config→ai→logger→config），且 config 包被迫知道 ai 包 |
| 4 | 只有 OpenAI 兼容一种模型格式 | 端口 + 三种协议适配器 | 你的明确要求 |
| 5 | `UserID` 一个字符串装 QQ 号/OpenID | `ConversationKey{AppID, Scene, SceneID}` + `Sender{OpenID}` | 官方平台「会话」与「发送者」是两套 openid；且随 AppID 变化 |
| 6 | `Send(Target, Content)`，`ReplyTo` 字段没人填 | `OutgoingMessage{Conv, Reply *ReplyRef, Text, Kind}`，`Reply` 为 nil 才表示主动消息 | 被动回复凭据是官方平台的硬约束，必须进类型系统 |
| 7 | 预建 `cron_tasks` 表「避免后续迁移」 | 迁移按迭代追加，不预建 | 你的明确要求；且预建的表 99% 会与最终设计不一致，反而更贵 |
| 8 | 硬编码 `data/napcat.db` | 路径来自配置 | 可测试（单测用 `t.TempDir()`）+ 可多环境 |
| 9 | 数据库「单例 + 启动时 panic」 | `store.Open(path)` 返回错误，`main` 处理 | 同上 |
| 10 | 没有「同会话串行」「入站幂等」「分段受被动次数限制」 | V1 必须具备 | 见 R1/R2/R3，这三条不处理就是必然出 bug |
| 11 | 限流（per-user 令牌桶）在 MVP 就预设 | V1 不引入；靠「同会话串行队列」天然限速 | YAGNI：单用户串行已经限制了滥用面；真需要时加在 `chat` 层 |
| 12 | 配置 YAML 但没提密钥不入库 | `config.yaml` 进 `.gitignore` + 环境变量覆盖 + 示例文件 | 见 §5.1 |
