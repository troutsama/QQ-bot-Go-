## 4.1 表设计的三条原则

| 原则 | 落地 | 影响的坑 |
|------|------|----------|
| **身份是二维的**：`(app_id, openid)`，不是裸 openid | 每张业务表都带 `app_id` | 沙箱/正式是两个 AppID；换 AppID 后裸 openid 会「指向不存在的用户」（R6） |
| **会话 ≠ 人**：会话表存「房间」，消息表存「谁说的」 | `conversations` 只存 `scene+scene_openid`；发送者在 `messages`/`turns` 上 | 群聊里 `group_openid`（房间）与 `member_openid`（人）不同；若把发送者写进会话表，一个群会被拆成 N 个会话 |
| **「轮」是一等公民** | 独立 `turns` 表，`messages` 挂在轮下 | 「最近 10 轮有效对话」若按「行数」算，V2 加工具调用后（一轮产生多行）算法必然返工（R5） |

**不预建未来表**。V1 只建下面 4 张。V2/V2.5/V3 各自追加迁移（§4.8 列出了到时候要加什么，用以证明 V1 的表**不需要改**）。

## 4.2 V1 表结构（迁移 `0001_init.sql`）

### `conversations` — 会话（房间）

```sql
CREATE TABLE conversations (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    app_id       TEXT    NOT NULL,          -- 机器人 AppID（沙箱/正式不同）
    scene        TEXT    NOT NULL,          -- 'c2c' | 'group'
    scene_openid TEXT    NOT NULL,          -- c2c: user_openid；group: group_openid
    created_at   INTEGER NOT NULL,          -- Unix 毫秒
    updated_at   INTEGER NOT NULL,
    UNIQUE (app_id, scene, scene_openid)
);
```

### `turns` — 一轮问答（上下文窗口的最小单位）

```sql
CREATE TABLE turns (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    conversation_id INTEGER NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    inbound_msg_id  TEXT    NOT NULL,       -- 平台消息 ID（被动回复凭据来源）
    sender_openid   TEXT    NOT NULL,       -- c2c: user_openid；group: member_openid
    sender_nickname TEXT    NOT NULL DEFAULT '',
    status          TEXT    NOT NULL,       -- 'processing' | 'ok' | 'failed' | 'filtered'
    error_kind      TEXT    NOT NULL DEFAULT '',  -- llm_auth / llm_rate_limited / llm_context_too_long / platform_send / internal
    model           TEXT    NOT NULL DEFAULT '',  -- 实际使用的模型名
    input_tokens    INTEGER NOT NULL DEFAULT 0,
    output_tokens   INTEGER NOT NULL DEFAULT 0,
    trace_id        TEXT    NOT NULL,
    started_at      INTEGER NOT NULL,
    finished_at     INTEGER,                -- NULL = 处理中被中断（崩溃/重启）

    -- 幂等：同一 AppID 下同一会话的同一入站消息只允许建一轮
    UNIQUE (conversation_id, inbound_msg_id)
);

CREATE INDEX idx_turns_window ON turns (conversation_id, status, id DESC);
```

> **幂等靠这个 UNIQUE 约束实现**，不额外建去重表：插入冲突 → `ON CONFLICT DO NOTHING` 且 `RowsAffected()==0` → 判定为「同 msg_id 已存在」，再读回既有轮。内存里再放一个 LRU 做快路径（避免重复走 SQL），但**真相在数据库**（进程重启/WS resume 后仍有效）。
>
> 注意：`status` 有一个中间态 `processing`，它让「重复推送」和「崩溃遗留」两件事可区分 —— 完整判定规则见 R15，这是整个模型里最容易写错的一处。

### `messages` — 轮内的消息

```sql
CREATE TABLE messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    turn_id    INTEGER NOT NULL REFERENCES turns(id) ON DELETE CASCADE,
    seq_in_turn INTEGER NOT NULL,           -- 轮内顺序，从 0 开始
    role       TEXT    NOT NULL,            -- 'user' | 'assistant' | 'tool'（V1 只有前两种）
    content    TEXT    NOT NULL,
    created_at INTEGER NOT NULL
);

CREATE INDEX idx_messages_turn ON messages (turn_id, seq_in_turn);
```

### `events` — 业务事件日志（admin API 的数据源）

```sql
CREATE TABLE events (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at      INTEGER NOT NULL,
    level           TEXT    NOT NULL,       -- 'debug' | 'info' | 'warn' | 'error'
    kind            TEXT    NOT NULL,       -- 见下表
    app_id          TEXT    NOT NULL DEFAULT '',
    trace_id        TEXT    NOT NULL DEFAULT '',
    conversation_id INTEGER,
    turn_id         INTEGER,
    platform_msg_id TEXT    NOT NULL DEFAULT '',
    message         TEXT    NOT NULL,       -- 人可读摘要
    payload         TEXT    NOT NULL DEFAULT ''  -- JSON 原文，截断到 config 里设定的大小
);

CREATE INDEX idx_events_time ON events (created_at DESC);
CREATE INDEX idx_events_kind ON events (kind, created_at DESC);
CREATE INDEX idx_events_trace ON events (trace_id);
CREATE INDEX idx_events_conv ON events (conversation_id, created_at DESC);
```

`kind` 取值（V1）：

| kind | 触发点 | payload 内容 |
|------|--------|-------------|
| `inbound` | 收到平台消息 | msg_id、scene、openid、文本长度、是否有附件 |
| `inbound_duplicate` | 幂等命中 | msg_id |
| `inbound_filtered` | 非文本消息 | msg_id、附件类型 |
| `llm_call` | 调用模型前 | protocol、model、消息条数、prompt 字符数 |
| `llm_result` | 模型返回 | 耗时、usage、stop_reason、回复字数 |
| `llm_error` | 模型失败（含重试次数） | 分类、HTTP 状态、原始错误（截断） |
| `outbound` | 每条消息发送成功 | msg_id、msg_seq、字数、第几段 |
| `outbound_error` | 发送失败 | 分类（含 `reply_quota_exhausted`）、原始错误 |
| `config_reload` | 配置热重载 | 变更字段列表、被忽略（需重启）的字段 |
| `bot_reconnect` | 重连 | 触发原因、耗时 |
| `system` | 启动/关闭/迁移 | 版本、迁移版本、PID |

> **日志双轨**：运行日志（含 SQL、第三方库日志）走**文件**（`logx`）；上面这些**业务事件**走 DB，因为它们要被 admin API 按 kind/会话分页查询。旧 TS 版把两者都塞进 DB（`log.maxEntries=5000` 环形），本方案拆开：文件负责排障，DB 负责审计与查询。

## 4.3 「最近 10 轮有效对话」的精确定义

这是 V1 的核心算法，必须无歧义。

### 有效轮（`status = 'ok'`）的判定

一轮只有**同时**满足以下条件才算 ok：

1. 用户文本非空（或有文本部分）
2. 不是被过滤的消息（非文本 → `filtered`）
3. **不是命令**（V2 起：命令轮 → `filtered`，绝不进入 AI 上下文 —— 见 R4）
4. 模型调用成功（至少有一段回复发送成功）

| 情况 | status | 进上下文？ | 记事件 |
|------|--------|-----------|--------|
| 正在处理中（尚未出结果，或崩溃遗留） | `processing` | ❌ | — |
| 正常问答 | `ok` | ✅ | inbound/llm_call/llm_result/outbound |
| 模型鉴权失败/限流/超时（重试后仍失败） | `failed` | ❌ | llm_error + outbound_error |
| 模型返回空回复 | `failed` | ❌ | llm_result（空）+ 兜底文案 |
| 发送第一条就失败（含次数耗尽） | `failed` | ❌ | outbound_error |
| 非文本消息 | `filtered` | ❌ | inbound_filtered |
| 命令消息（V2 起） | `filtered` | ❌ | inbound（kind=command） |
| 重复推送 | **不建轮** | ❌ | inbound_duplicate |

### 取窗口的算法

```sql
-- 第 1 步：最近 10 个有效轮（倒序取，再反转）
SELECT id FROM turns
WHERE conversation_id = ? AND status = 'ok'
ORDER BY id DESC
LIMIT ?;                                   -- ? = cfg.chat.context_turns，默认 10

-- 第 2 步：这些轮的全部消息（含 V2 起的 tool 消息），按轮内顺序
SELECT m.turn_id, m.seq_in_turn, m.role, m.content, m.created_at
FROM messages m
WHERE m.turn_id IN (...)
ORDER BY m.turn_id ASC, m.seq_in_turn ASC;
```

**为什么按 `turns` 而不是按 `messages` 取**：V2 引入工具调用后，一轮会产生 `user` + `assistant(tool_calls)` + `tool(result)` + `assistant(文本)` 共 4 行。如果按行取「最近 20 行」，会取到半截轮（工具结果丢了、或只有工具调用没有最终回答），模型行为会诡异。按轮取 + 整轮全取，V2 无需改算法。

### 渲染

1. 每轮的 user / assistant 消息前加本地时间前缀 `[MM-DD HH:mm] `（**保留 TS 版行为**，让模型知道上一轮距今多久）
2. 由配置 `chat.context_time_prefix` 控制开关（默认 `true`）
3. 拼成 `llm.Request.Messages`，`System` 单独从配置取（不进 Messages，见 §3.3.1）

> 时区问题：时间前缀用**进程本地时区**。若部署到 UTC 机器上而用户在东八区，前缀会错位 —— 配置里加 `timezone`（默认 `Asia/Shanghai`）并用 `time.LoadLocation` 显式加载，不依赖 `time.Local`。

## 4.4 与分段相关的参数

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `chat.max_reply_segments` | `3` | 单次回复最多分几段（单聊被动回复上限 4，留 1 次余量） |
| `chat.segment_max_chars` | 待实测（**T2**，暂用 `1500`） | 单条消息字符上限，官方真实上限见 06 待实测 |
| `chat.segment_split_on` | `"\n\n"` | 优先在空行切分；次选句号；最后硬切 |
| `chat.context_turns` | `10` | 上下文轮数 |
| `chat.context_time_prefix` | `true` | 时间前缀开关 |
| `chat.reply_typing_indicator` | `false` | 是否发「输入中」（待实测 T3，默认关） |

长回复处理顺序：按 `max_reply_segments` 决定段数 → 每段按 `segment_split_on` 优先切 → 仍超长则硬切 → 最后一段超长则截断并追加「（内容过长已截断）」。

## 4.5 迁移机制

### 规则

| 规则 | 说明 |
|------|------|
| 版本标记 | `PRAGMA user_version`（SQLite 内建，无需额外表） |
| 迁移文件 | `internal/store/migrations/0001_init.sql`、`0002_xxx.sql`…，用 `//go:embed migrations/*.sql` 编进二进制 |
| 执行 | `user_version = N` → 按序执行 `N+1..` 的迁移，**每个迁移在单个事务内**，成功后 `PRAGMA user_version = M` |
| 失败处理 | **启动失败并退出**（非 0 退出码），不静默继续。迁移中断后重启会从 `user_version` 处重试 |
| 禁止 | ❌ 修改已发布的迁移文件（会导致已升级的库与新库 schema 不一致） |
| 幂等 | 每个迁移只跑一次（由 `user_version` 保证），所以**不需要** `IF NOT EXISTS`；但建索引可用 `IF NOT EXISTS` 无害 |

### 版本号段（预留，避免冲突）

| 版本 | 迭代 | 内容 |
|------|------|------|
| `0001` | **V1** | `conversations` / `turns` / `messages` / `events` |
| `0002` | V2 | `users`（身份锚点 + 个人偏好）、命令相关 |
| `0003` | V2.5 | `school_credentials` / `school_timetable` / `school_meta` / `school_sessions` / `user_settings` |
| `0004` | V3 | `cron_tasks` / `cron_runs` |
| `0005+` | 以后 | `memory_*`（长期记忆） |

## 4.6 连接、PRAGMA 与连接池

### DSN（`modernc.org/sqlite` 的 `_pragma` 语法）

```
file:data/bot.db?_pragma=journal_mode(WAL)
                &_pragma=busy_timeout(5000)
                &_pragma=foreign_keys(1)
                &_pragma=synchronous(NORMAL)
```

| PRAGMA | 为什么必须 |
|--------|-----------|
| `journal_mode(WAL)` | 读写不互斥，读不被写阻塞 |
| `busy_timeout(5000)` | 并发写时等 5s 而不是立刻报 `SQLITE_BUSY` |
| `foreign_keys(1)` | **SQLite 的外键默认关闭，且是 per-connection 的** —— 必须在 DSN 里设，写成 `db.Exec("PRAGMA foreign_keys=ON")` 只对那一条连接生效，池里其它连接仍不校验外键 |
| `synchronous(NORMAL)` | WAL 下的常用折中（`FULL` 太慢，`OFF` 掉电可能损坏） |

### 连接池

```go
db.SetMaxOpenConns(1)   // V1 的选择
db.SetMaxIdleConns(1)
db.SetConnMaxLifetime(0)
```

- **为什么是 1**：SQLite 只有一个写者。设 1 就等于「串行化所有访问」，从根上消除 `SQLITE_BUSY`，且本项目负载极低（个人自用）。这是最简单且**绝不会错**的选择。
- **升级路径**：真出现性能瓶颈时，改为「1 个写连接（单独 `*sql.DB`）+ N 个读连接」，配合 WAL 与 `busy_timeout`。改动局限在 `store` 包内，不影响其它包。
- **不要**用 `SetMaxOpenConns(1)` 的同时开 WAL 又指望并发读 —— 它们不矛盾，只是读也被串行化了；文档化这个取舍即可。

### 时间存法

统一 **Unix 毫秒（INTEGER）**，不用 SQLite 的 TEXT 日期。理由：跨时区显示由应用层负责，DB 里只存绝对时刻，排序和索引都干净。

## 4.7 增长控制

| 表 | 增长源 | V1 策略 |
|----|--------|---------|
| `events` | 每轮 4~6 条，长期最大 | 配置 `log.event_retention_days`（默认 14）；**启动时清理一次**，之后每 24h 清理一次（一个简单 goroutine） |
| `messages` / `turns` | 每轮 2~4 行 | **不自动清理**（上下文数据，是功能资产）。预留 admin 端点 `POST /admin/maintenance/cleanup?vacuum=1`（V1 可选，见 §5.4） |
| `conversations` | 每个新用户 1 行 | 无需清理 |

> 不做「环形上限」（TS 版的 `log.maxEntries=5000`）—— 那是为了配合前端只显示最近 5000 条。DB 用「按时间保留」更直观，且不影响分页查询的历史深度。

## 4.8 各迭代将新增的表（V1 不建，仅证明无需改 V1 表）

| 迭代 | 新表 | 用途 | 与 V1 表的关系 |
|------|------|------|----------------|
| V2 | `users(app_id, openid, nickname, last_seen_at, system_prompt, union_openid)` | `/prompt` 的个人提示词；`union_openid` 预留跨 AppID 打通（官方 `dto.User.UnionOpenID`） | 逻辑引用 `turns.sender_openid`，无需改 V1 表 |
| V2 | `commands_log`（可选） | 命令调用审计 | 独立 |
| V2.5 | `school_credentials` / `school_timetable` / `school_meta` / `school_sessions` / `user_settings`(EAV) | 对照 TS 版 `school/*` + `user-config.ts` | 通过 `users.id` 关联 |
| V3 | `cron_tasks` / `cron_runs` | 定时任务与其执行记录 | 通过 `users.id` 关联 |
| 以后 | `memory_profile` / `memory_summary` / `memory_entries` | 长期记忆（对照 TS 版 `lib/memory/`） | 通过 `users.id` 关联 |

> 注意 V2 才引入 `users` 表，这是刻意的：V1 只有私聊且没有个人化设置，引入 `users` 只会是一张「只存 openid 和昵称」的空壳。V1 的 `turns.sender_openid` / `sender_nickname` 已经把数据留下来了，V2 建 `users` 时可以从 `turns` 回填。

### 密钥管理（V1 就必须做对）

| 措施 | 说明 |
|------|------|
| `config.yaml` 进 `.gitignore`，只提交 `config.example.yaml` | 旧 TS 版的 `data/config.json` 也是不入库的；Go 版同理 |
| 支持 `${VAR}` 占位符 | 加载时对文件**原文**做 `${VAR}` / `${VAR:-默认值}` 替换；**变量未定义且无默认值时直接报错退出**（避免用空密钥静默启动） |

## 5.2 热重载边界（三档）

`config.Diff(old, new)` 把每个字段归入三档之一。**reload 时对不可热载的变更记录 `warn` 事件并在响应里返回**，绝不静默。

| 档位 | 字段 | 生效方式 | 实现代价 |
|------|------|----------|----------|
| **① 立即热载** | `llm.*`（含 protocol/base_url/api_key/model/temperature/max_tokens/timeout/system_prompt）、`chat.*`、`log.level`、`log.event_*` | 原子替换持有的配置快照（`atomic.Pointer[Config]`），下一次调用即生效 | 低 |
| **② 需重连** | `bot.qqbot.app_secret`（AppID 不变） | 重建 token source + 断开重连 WS 并重新鉴权。**AppID 未变 → openid 不变 → 历史数据继续有效** | 中 |
| **③ 必须重启进程** | `bot.provider`、`bot.qqbot.app_id`、`bot.qqbot.sandbox`、`server.listen`、`database.path` | 返回 409 + 明确的「需执行 `POST /admin/system/restart`」提示 | 无需实现 |
| 特殊情况 | `log.file` | 可热载，但需**重建 writer**（关闭旧文件句柄 → 打开新文件），实现上等同于 ① | 低 |

> **为什么换 AppID 必须重启而不是重连**：AppID 变了意味着 `user_openid` 全部作废，库里已有数据的 `app_id` 列将对不上 —— 这不是「重新连一下」能解决的，它涉及数据语义（见 R6）。程序要做的是**拒绝**并让用户明确决策。

- 若**消耗次数**：默认关闭，仅当 `max_reply_segments` 调低时才可用

### 鉴权与暴露面

| 项 | 决定 |
|----|------|
| 鉴权 | `Authorization: Bearer <admin_token>`，用 `crypto/subtle.ConstantTimeCompare` 比较（防时序侧信道） |
| token 为空 | **拒绝启动**（不给默认值）。旧 TS 版的默认 `napcat-admin-token` 是必须避免的坑 |
| 监听地址 | 默认 `127.0.0.1:8081`；改 `0.0.0.0` 时启动日志打 `warn` |
| 高危端点 | `restart` / `reconnect` / `debug/inject` / `maintenance/cleanup` 都写 `events`（kind=`system`），便于事后追溯 |
| 404 泄漏 | 未匹配路由返回统一的 JSON 404，不回显内部包名/堆栈 |

### `POST /admin/debug/inject` 为什么值得进 V1

它是**唯一能让你在不碰 QQ 的情况下验证整条链路**的手段，对「手写 + 边写边测」的开发方式价值极高：

```bash
curl -X POST localhost:8081/admin/debug/inject \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"scene":"c2c","openid":"debug-user-1","text":"你好"}'
```

响应里带每步耗时（幂等检查 / 取上下文 / 调模型 / 分段发送）与最终分段结果，可以直接看到上下文里到底拼了什么（若 `log.level=debug`）。旧 TS 版的 `/api/test/inject` 提供过同样能力。

## 5.5 重启三态（对应你的 Q3 追问）

### 结论：不做「① 替代 ②」，而是**分层**

| 层 | 机制 | 覆盖场景 |
|----|------|----------|
| 能力层 | `reload` / `reconnect` | 90% 的日常变更，无需断进程 |
| 入口层 | `restart`（`syscall.Exec` 自我重启） | 结构性配置变更（端口、DB 路径、AppID、Provider 切换） |
| **兜底层** | **外部进程管理器** | **进程真的坏了的情况**（死锁、panic 循环、API 也无响应） |

**关键认知**：`restart` 端点和 `reload` 端点**走的是同一个已经坏掉的 HTTP 服务**。如果进程真的半死，你发不出任何请求。所以「进程坏了怎么办」这个问题**只能由外部进程管理器解决**：

| 环境 | 方案 |
|------|------|
| 本机开发 | `Makefile` 的 `make run` + 一个 `scripts/dev-watch.sh`（或直接用 `until ./bin/botd; do sleep 1; done` 一行循环） |
| macOS 常驻 | `launchd` plist（`KeepAlive=true`） |
| Linux 服务器 | `systemd` unit（`Restart=always`） |
| 容器 | `docker run --restart=always` |

**V1 只做**：`reload` / `reconnect` / `restart` 三个端点 + `health` 端点。部署形态的 unit/plist 示例放 V3 的文档，不进 V1 代码。

### `syscall.Exec` 自我重启的实现要点

1. **先返回响应再 exec**：和旧 TS 版 `setTimeout(process.exit, 1000)` 同理。顺序必须是
   `写 202 响应 → Flush → 优雅关闭（见 §5.8）→ syscall.Exec`
2. **取二进制路径用 `os.Executable()`**，不用 `os.Args[0]`（后者可能是相对路径或符号链接）
3. **`go run` 场景必须检测并拒绝**：`go run` 会把二进制放在 `/tmp/go-buildXXXX/b001/exe/...`，exec 它等于运行一个可能已被删除的临时文件。检测方式：拿 `os.Executable()` 的路径判断是否位于系统临时目录下 / 是否包含 `go-build`，命中则返回：
   `409 {"error":"当前进程由 go run 启动，无法自我重启；请使用 make run 或运行已编译的二进制"}`
4. **exec 失败要兜底**：`syscall.Exec` 返回错误时不退出，记录 `error` 事件并返回 500（否则会出现「进程已关闭但没起来」的最坏情况）
5. **环境与工作目录**：`syscall.Exec(path, os.Args, os.Environ())`；`config.yaml` 与 `data/` 用**相对路径**时必须保证 cwd 不变 —— 更稳的做法是启动时把所有相对路径解析成绝对路径并记日志

## 5.6 数据库生命周期（回答你的「要不要单独启动 SQLite」）

**SQLite 没有服务进程，不存在「先启动数据库」这一步。** 正确做法：

```
main():
  1. 解析配置（含 database.path）
  2. os.MkdirAll(filepath.Dir(dbPath)) + MkdirAll(logDir)
  3. store.Open(dbPath)        → sql.Open + Ping + 设置连接池（见 §4.6）
  4. store.Migrate(ctx)        → 按 PRAGMA user_version 推进；失败 → 退出（非 0）
  5. 构建适配器与服务
  6. 启动 admin HTTP
  7. provider.Start(ctx)
  8. chat.Run(ctx)
  9. 等信号 → 优雅关闭
```

| 做法 | 结论 |
|------|------|
| ❌ 用脚本建库/建表 | 脚本和程序各建一次，schema 迟早漂移；且「表由代码定义」这条原则会被破坏 |
| ❌ 用脚本「启动 SQLite」 | SQLite 无服务进程，此路不通 |
| ✅ 进程内打开 + 启动时自动迁移 | 唯一正解。这一条同时回答了「数据库表在各阶段处理」：迁移文件按迭代追加（§4.5） |
| ✅ 脚本只做 `make run` / `make test` / `make fmt` | 脚本负责开发流程，不负责数据 |

**为什么不给 `store` 做全局单例**（旧方案的 `db.GetDB()` + `panic`）：

- 单测要跑迁移时可以用 `t.TempDir()` 建一个独立库 → 每个测试互不干扰；全局单例做不到
- 启动失败时 `main` 能返回错误码并给出清晰日志，而不是 `panic` 时先经过一段难看的栈
- `store.Open` 返回 `(*Store, error)`，`Store` 上挂方法（`store.Conversations()` 等），所有 SQL 只在这个包内

## 5.7 日志：双轨 + trace_id

| 轨 | 载体 | 内容 | 谁查 |
|----|------|------|------|
| 运行日志 | `data/logs/bot.log`（轮转）+ stdout | 启动/关闭、迁移、重连、SQL（debug）、第三方库日志、错误堆栈 | 开发者（`tail -f`） |
| 业务事件 | SQLite `events` 表 | §4.2 表格里那些 kind | admin API / 审计 / 排障 |

### 实现约定

- 底层用标准库 **`log/slog`**（Go 1.21+，不引 logrus）。`logx` 只做三件事：配置 handler（文件+控制台双写）、注入稳定字段、提供 `Redact`
- **trace_id**：每条入站消息生成一个（`msgID` 的短哈希或随机 12 位 hex），通过 `context.Context` 传递，自动进所有日志与事件行。排障时 `grep <trace_id>` 就能拉出这一条消息的完整生命周期
- **轮转**用 `gopkg.in/natefinch/lumberjack.v2`（约 200 行的成熟库）。**故意不手写轮转** —— 轮转的边界条件（跨天、大小切换时的部分行、并发写）是纯 bug 温床，学习收益低。因为 `logx` 是门面，将来想换成自研实现只改 `logx/rotate.go`
- **botgo 的日志接入**：botgo 自带 `log` 包，必须重定向到 `logx`（参考 botgo `examples/custom-logger`），否则会出现两套格式、且它的日志不进文件

## 5.8 优雅关闭清单（顺序不能错）

```
收到 SIGTERM / SIGINT（或 restart 端点触发）
  ↓
1. 停止接收新事件        provider.Stop(ctx)（或 cancel 根 ctx，让 Events 通道关闭）
  ↓
2. 等在途 turn 完成      最多等 cfg.chat.shutdown_grace（默认 15s）
                         超时则放弃并 warn（未完成轮留在 turns 里 finished_at=NULL）
  ↓
3. 关闭 admin HTTP        http.Server.Shutdown(ctx)，等正在处理的请求
  ↓
4. flush 日志            关闭 logx 的文件句柄
  ↓
5. 关闭 DB               db.Close()（WAL 会做 checkpoint）
  ↓
6. 退出分支              restart → syscall.Exec；否则 os.Exit(0)
```

三个容易做错的地方：

1. **不要在关闭时等太久**。被动回复窗口有限（群聊 5 分钟），但更重要的是用户等待体验。15s 是个折中；超时后**放弃比继续等更好**。
2. **`finished_at IS NULL` 是特征而不是 bug**：它代表「这一轮被中断」，下次启动时可以被识别（并可选地在启动日志里报告「上次有 N 轮未完成」）。
3. **信号处理要注册在组合根**，不要散落在各包的 `init()` 里（否则测试时无法控制）。

## 5.9 构建、依赖与 Makefile

### 依赖清单（刻意保持很小）

| 依赖 | 用途 | 为什么不用替代 |
|------|------|---------------|
| `github.com/tencent-connect/botgo` | QQ 官方 SDK | 你已用它测通；且已确认包含 v2 单聊/群聊发送端点 |
| `modernc.org/sqlite` | SQLite 驱动（纯 Go） | 无 CGO → Mac 上可直接交叉编译 Linux 二进制（`mattn/go-sqlite3` 需 CGO） |

| `gopkg.in/natefinch/lumberjack.v2` | 日志轮转 | 见 §5.7，手写收益低 |
| **标准库** | `net/http`、`log/slog`、`context`、`errors`、`embed`、`sync/atomic`、`crypto/subtle`、`testing` | 全部够用，不引框架 |

**刻意不引入**：Web 框架（gin/echo）、ORM（gorm）、依赖注入库（wire/fx）、配置库（viper）、日志库（logrus/zap）。
理由：V1 只有 12 个 HTTP 端点、1 个数据源、1 个模型协议家族。以上每一样在学弟阅读代码时都是「多一层要理解的东西」，而收益是零。等真需要时再加，且因为走了端口/适配器，替换面很小。

### Makefile 目标

```make
run:            go run ./cmd/botd            # 注意：不可自我重启（见 §5.5）
```

`-migrate-status` 之类的只读子命令挂在同一二进制上（用 `flag` 解析），**不新开 `cmd/` 子目录**。
