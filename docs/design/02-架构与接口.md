## 2.1 一句话架构

**端口 / 适配器 + 显式组装**：业务编排（`chat`）只依赖接口（端口），QQ 平台与模型协议都是可替换的适配器，所有对象的创建集中在一个组合根（`cmd/botd/main.go`），**全项目没有全局单例**。

                                    │ 注入

**依赖方向铁律**：箭头只能从「具体」指向「抽象」，从「外」指向「内」。

```
provider/*  ──▶  platform(port)  ◀──  chat  ──▶  store
provider/*  ──▶  llm(port)       ◀──  chat
admin       ──▶  chat / store / config / platform(重启用)
chat        ──▶  ✗ 禁止 import provider/qqbot 或 provider/anthropic
```

违反判定法：**`chat` 包里出现 `"github.com/tencent-connect/botgo"` 或 `"openai"` 字样即为设计事故。**

## 2.3 各包职责与「XX 代码放哪」的答案

| 你问的问题 | 答案 | 具体文件 |
|-----------|------|----------|
| **AI 部分的代码放哪？** | `internal/llm/`（端口 + 中性数据模型 + 三个协议适配器） | `llm/port.go`、`llm/provider/*/client.go` |
| **管理用户输入的代码放哪？** | `internal/chat/pipeline.go`（V1 是「收文本 → 走 AI」；V2 在此**插入命令判定步骤**，命令优先于 AI） | `chat/pipeline.go` |
| **发送消息的代码放哪？** | 「翻译成官方协议」在 `internal/platform/provider/qqbot/outbound.go`；「决定发什么、分几段」在 `internal/chat/split.go` + `chat/service.go` | 见左 |
| 会话身份/OpenID 处理 | `internal/platform/scene.go`（平台侧）+ `internal/session/key.go`（持久化侧） | — |
| 数据库读写 | `internal/store/`（每个聚合一个文件）；**SQL 只出现在 store 包内** | — |
| HTTP 接口 | `internal/admin/`（一个端点一个文件或一个 handler 函数） | — |
| 配置 | `internal/config/` | — |
| 日志 | `internal/logx/`（写日志）+ `internal/store/eventlog.go`（业务事件入库） | — |
| 定时任务（V3） | 新增 `internal/schedule/`（引擎）+ `internal/store/schedule.go`（表）；命令入口在 `chat/pipeline.go` | — |
| 学校能力（V2.5） | 新增 `internal/school/`（CAS/课表/电费）+ `store/school.go` | — |

### 为什么 `chat` 是「编排」而不是「handler」

旧方案叫 `internal/handler`，容易变成一个什么都往里塞的杂物间（它同时承担 AI 调用、上下文、发送、限流、日志）。这里拆开：

- `chat.Service` = **生命周期与队列**（拿事件、去重、入队、出队、出站、错误兜底）
- `chat.Pipeline` = **单条消息的处理步骤**（可插拔的 []Step，V1 只有 1 个 AI 步骤，V2 在头部插命令步骤）
- `chat/context.go` / `chat/split.go` = **纯函数**（无 IO，最容易写单测，也是学弟最好的练手对象）

## 2.4 「工厂 + 策略」在 Go 里的形态（重要）

你在 TS/Java 里习惯的写法是「接口 + 实现类 + 注册表 + `init()` 自动注册」。**Go 里 v1 不建议这么做**，理由：

| 旧方案（注册表 + `init()`） | 本项目方案（组合根 switch） |
|---------------------------|---------------------------|
| `init()` 隐式副作用，读代码要全局搜谁注册了什么 | 只在 `platform/factory.go` / `llm/factory.go` 两处，一眼看完 |
| 单测里无法控制注册内容，只能测到「全部实现」 | 单测直接 `platform.New(cfg)` 或干脆手塞 mock |
| 重复注册要 `panic` | 无 |
| 实现 ≥5 个、或要插件化时才划算 | **v1 只有 1 个 bot + 3 个 llm 实现，注册表是过度设计** |

**落地形态**（策略 = 接口，工厂 = 显式函数）：

```go
// internal/platform/factory.go
func New(cfg config.BotConfig, log *slog.Logger) (Provider, error) {
    switch cfg.Provider {
    case "qqbot":
        return qqbot.New(cfg.QQBot)
    case "mock":                       // 本地开发/单测：不发真实消息，打印到 stdout
        return mock.New()
    default:
        return nil, fmt.Errorf("platform: 未知 provider %q（可用：qqbot, mock）", cfg.Provider)
    }
}
```

`llm/factory.go` 同理，按 `cfg.LLM.Protocol` 三分支。

**升级路径**：真需要插件化时，把 `switch` 换成 `map[string]func(...) (T, error)` + `Register()`，调用点不变。现在不需要。

> 关于配置里的 key 名：注意 `platform.provider`（`qqbot`/`mock`）和 `llm.protocol`（`openai-chat`/`openai-responses`/`anthropic`）是**两个独立的切换点**，因为它们的变化节奏不同（换平台 vs 换模型服务商）。

## 2.5 为什么不用 `pkg/` 目录

Go 社区的 `pkg/` 惯例只在「这些包要被仓库外的人 import」时才有意义。本项目是应用（不是库），所有代码都是 `internal/`：

- `internal/` 由编译器强制「外部不可 import」，等于免费的边界检查
- 未来若真要把 `platform` 或 `llm` 抽成可复用库，那时再新开一个仓库或加 `pkg/`，一次移动即可

同理**不预先建** `cmd/<其他子命令>/`：V1 只有一个二进制。

> 本节是**接口草案**，不是实现。目的：先在纸面上把「官方平台的硬约束」翻译成类型，写代码时就不容易漏。

## 3.1 通信底座端口 `internal/platform/port.go`

### 3.1.1 类型定义

```go
package platform

type Scene string

const (
    SceneC2C   Scene = "c2c"   // 单聊
    SceneGroup Scene = "group" // 群聊（接口预留，V1 不实现）
)

// ConversationKey 标识「一段会话」。注意它不等于「一个人」。
//
// 官方平台的两条硬约束：
//  1. 会话 ID 和发送者 ID 是两套不同的 openid：
//       c2c   → 会话=user_openid，发送者=user_openid（同一值）
//       group → 会话=group_openid，发送者=member_openid（不同值）
//  2. 所有 openid 都随 AppID 变化。沙箱与正式是两个 AppID，
//     开发时两边数据会共用一个库 → AppID 必须进 key，否则数据混在一起。
type ConversationKey struct {
    AppID   string // 机器人 AppID（沙箱/正式不同）
    Scene   Scene
    SceneID string // c2c: user_openid；group: group_openid
}

// Sender 消息发送者。
type Sender struct {
    OpenID   string // c2c: user_openid；group: member_openid
    Nickname string // 官方事件里通常没有昵称，V1 允许为空
}

// IncomingMessage 平台无关的入站消息。
type IncomingMessage struct {
    MsgID     string          // 平台消息 ID —— 被动回复的唯一凭据，**必带**
    EventID   string          // 事件类回调的凭据（如按钮交互），消息类为空
    Conv      ConversationKey
    Sender    Sender
    Text      string          // 已提取的纯文本（可能为空，见 Attachments）
    HasAttachment bool        // 是否含非文本段（图片/语音/文件/ark）
    MentionedBot  bool        // 群消息是否 @ 了机器人（V1 无群，预留）
    Timestamp time.Time
    Raw       any             // 平台原始载荷（排障用，不进 DB 正文）
}

// OutKind 出站消息种类。
type OutKind string

const (
    OutText   OutKind = "text"   // 普通文本
    OutTyping OutKind = "typing" // 「输入中」状态（官方 msg_type=6，见 06 待实测 T3）
)

// ReplyRef 被动回复凭据。
//
// 官方规则：回复一条入站消息必须携带它的 msg_id，并可携带递增的 msg_seq；
// 同一 msg_id 下的 msg_seq 若不递增会被平台去重（错误码 40054005）。
// 且被动回复有次数上限（单聊 4 次 / 群聊 5 次）与时效窗口（单聊 60min / 群聊 5min）。
type ReplyRef struct {
    MsgID   string
    EventID string

    seq atomic.Uint32 // 私有：Send 内部原子递增，不允许外部设置
}

func NewReplyRef(msgID, eventID string) *ReplyRef

// NextSeq 返回本次使用的 msg_seq。
// 起始值假定为 1（自增到 1,2,3…）；若实测表明必须从 0 开始，只改这一处（见 06 T5）。
func (r *ReplyRef) NextSeq() uint32

// OutgoingMessage 平台无关的出站消息。
type OutgoingMessage struct {
    Conv  ConversationKey
    Reply *ReplyRef // nil = 主动消息（受限，V1 只在极少数非用户场景使用）
    Kind  OutKind
    Text  string
}

// SentMessage 发送结果。
type SentMessage struct {
    MsgID string
    Seq   uint32
}

// Status 连接状态。
type Status string

const (
    StatusDisconnected Status = "disconnected"
    StatusConnecting   Status = "connecting"
    StatusConnected    Status = "connected"
)

// Provider 通信底座端口（策略）。
type Provider interface {
    // Name 适配器名（"qqbot" / "mock"）
    Name() string

    // Start 建立连接并开始投递事件。应尽快返回；事件循环在内部 goroutine。
    // 返回错误表示建连失败（由上层决定是否重试）。
    Start(ctx context.Context) error

    // Stop 优雅断开：停止接收新事件、等待内部 goroutine 退出、关闭 Events 通道。
    Stop(ctx context.Context) error

    // Status 当前连接状态。
    Status() Status

    // Send 发送一条消息。阻塞直到平台返回或 ctx 超时。
    // Reply 为 nil 时是主动消息（受频控，且用户可关闭）。
    Send(ctx context.Context, msg OutgoingMessage) (SentMessage, error)

    // Events 入站事件流。Provider 关闭时该通道被 close。
    Events() <-chan IncomingMessage
}
```

### 3.1.2 设计要点（每条都对应一个真实的坑）

| 设计 | 为什么不这样就会出 bug |
|------|----------------------|
| `Reply *ReplyRef` **指针**，nil 才表示主动消息 | 若用 `ReplyRef` 值类型 + 零值判断，实现者很容易「忘了填 msg_id」→ 平台按**主动消息**处理 → 受频控、用户可能关闭开关、群里完全发不出。用指针把「你想干什么」变成编译期必须表态 |
| `msg_seq` 计数在 `ReplyRef` 内部原子递增 | 多段回复是并发/循环发送的，外部维护计数器必然出现竞态；且平台**按 (msg_id, msg_seq) 去重**，序号重复 = 第 2 段被静默丢弃 |
| `ConversationKey` 带 `AppID` | 沙箱与正式两套 openid 写进同一个库 → 调试时数据互相污染，且换 AppID 后旧数据「指向不存在的用户」 |
| `Sender.OpenID` 与 `Conv.SceneID` **分开** | 群里这两个值不同（member_openid vs group_openid）。V1 只做私聊时它们恰好相等，一旦 V1 图省事合并成一个字段，V2 加群聊就要改表 + 改接口 |
| `HasAttachment` 而不是把图片转文字 | V1 只支持文本，必须能区分「空文本因为用户发了图」和「用户发了空白」→ 见 §1.3 的处理表 |
| `Events()` 用 channel 而非回调注册 | 回调注册（`RegisterHandler`）会带来「谁注册了什么」的隐式全局状态，且难以在单测里按需构造事件流 |

### 3.1.3 分段与被动回复次数的关系（V1 必须处理）

一次入站消息能被动回复的次数是**有限**的：

| 场景 | 窗口 | 可回复次数 |
|------|------|-----------|
| 单聊 | 60 分钟 | 4 次 |
| 群聊 | 5 分钟 | 5 次 |

因此「把长回复拆成 6 段」在单聊里第 5、6 段必然失败。处理方案：

1. **配置项** `chat.max_reply_segments`（默认 **3**，单聊上限 4 留 1 次余量给错误提示）
2. `chat/split.go` 分段时**最多切出 N 段**，超出部分合并进最后一段
3. 若最后一段仍超单条长度上限，**截断并追加「（内容过长已截断）」**
4. `platform.ErrReplyQuotaExhausted`：适配器发送失败且错误码表明次数耗尽时返回该哨兵错误，`chat` 层记录事件、停止重试、不再继续发后续段

> 「输入中」状态（`OutTyping`）是否消耗次数**未知**，见 06 待实测 T3。若消耗次数，则 V1 把 `OutTyping` 关掉。

### 3.1.4 未来接 Webhook 的预留（V1 不实现）

官方已公告 WS 事件链路将下线、webhook 是新链路（要求 HTTPS + `plain_token`/`event_ts` 签名验签）。届时只加一个适配器，`chat` 一行不改：

```go
// internal/platform/receiver.go（未来新增，V1 不建）
// WebhookReceiver 由「能接收 HTTP 回调」的适配器实现。
type WebhookReceiver interface {
    // Path 回调路径（例如 "/qqbot/callback"）
    Path() string
    // Verify 验签（plain_token + event_ts 计算签名）
    Verify(r *http.Request, body []byte) error
    // Handle 解析回调并投递到 Events()
    Handle(w http.ResponseWriter, r *http.Request)
}
```

`admin.Server` 注册路由时：

```go
if r, ok := provider.(platform.WebhookReceiver); ok {
    mux.HandleFunc(r.Path(), r.Handle)   // 与 admin API 共用同一个 HTTP 服务端口
}
```

这也是为什么把「接收」和「发送」放在同一个 `Provider` 里而在 03 里预留 `WebhookReceiver`：webhook 模式下**没有长连接**，`Start` 只启动内部处理循环，接收交给 HTTP handler。

## 3.2 `provider/qqbot` 适配器要点

### 3.2.1 botgo 映射（已核实 SDK 支持 v2 单聊/群聊发送）

| 我们的类型 | botgo API |
|-----------|-----------|
| 建连 | `token.StartRefreshAccessToken(ctx, tokenSource)` + `botgo.NewOpenAPI(appID, tokenSource)` + WS session |
| 接收单聊 | `event.C2CMessageEventHandler` → `*dto.WSC2CMessageData`（= `dto.Message`） |
| 接收群聊 | `event.GroupATMessageEventHandler` → `*dto.WSGroupATMessageData`（V1 不注册） |
| 发送单聊 | `api.PostC2CMessage(ctx, userOpenID, &dto.MessageToCreate{Content, MsgID, MsgSeq})` |
| 发送群聊 | `api.PostGroupMessage(ctx, groupOpenID, &dto.MessageToCreate{...})` |
| 发送中状态 | `dto.MessageToCreate` 的 `msg_type=6`（待实测 T3） |
| 撤回 | `api.RetractC2CMessage` / `RetractGroupMessage`（V1 不用） |
| 底层路径 | SDK 内 `openapi/v1/resource.go` 里就是 `/v2/users/{user_id}/messages`、`/v2/groups/{group_id}/messages` |

**字段映射**：

| IncomingMessage | 来源 |
|-----------------|------|
| `MsgID` | `dto.Message.ID` |
| `Conv.AppID` | 配置里的 AppID（事件里没有） |
| `Conv.Scene` | 事件类型决定（C2C → `SceneC2C`） |
| `Conv.SceneID` | C2C 时 = `dto.Message.Author.ID`（openid） |
| `Sender.OpenID` | 同上（C2C）；群聊时 = `Author.ID`（member_openid）而 `SceneID` = `Message.GroupID` |
| `Text` | `dto.Message.Content`（群 @ 消息的事件里 content 已自动去掉 @ 前缀） |
| `HasAttachment` | `len(dto.Message.Attachments) > 0` |

### 3.2.2 适配器内部必须处理的 4 件事

1. **botgo 自带的 logger 接到我们的 `logx`**（botgo 有独立 `log` 包，不接管会出现两套格式）。参考 botgo `examples/custom-logger`。
2. **重连不能重复注册事件 handler**。botgo 的 WS 断开会自动 resume；若把 `event.RegisterHandlers` 放在重连回调里，会出现「一条消息被处理两次」。注册只在 `Start` 里做一次。
3. **识别「次数耗尽」错误码**，映射为 `platform.ErrReplyQuotaExhausted`（见 3.1.3）。
4. **`Send` 必须是并发安全的**，因为 `chat` 可能同时给不同会话发消息。

### 3.2.3 `provider/mock`（V1 就要有，不是可选）

一个把 `Send` 打印到 stdout、从 stdin 或固定脚本注入事件的内存实现。价值：

- `chat` 全链路单测**不连 QQ、不调模型**即可运行（§1.5 质量验收）
- 本地开发时无需真实的沙箱机器人也能调上下文/分段逻辑
- `config.yaml` 里 `platform.provider: mock` 即可切换 —— 这也顺带验证了「工厂+策略」真的能切

## 3.3 模型端口 `internal/llm/port.go`

### 3.3.1 内部中性模型（与协议无关）

```go
package llm

type Role string

const (
    RoleUser      Role = "user"
    RoleAssistant Role = "assistant"
    RoleTool      Role = "tool" // 工具结果（V1 不产生，类型先留着）
)

type Message struct {
    Role        Role
    Text        string       // 文本内容（可为空，若只有工具调用）
    ToolCalls   []ToolCall   // assistant 发起的调用（V1 恒空）
    ToolResults []ToolResult // role=tool 时的结果（V1 恒空）
}

type ToolCall struct {
    ID        string
    Name      string
    Arguments string // 原始 JSON 字符串（不解析，避免不同协议格式差异）
}

type ToolResult struct {
    CallID string
    Output string
}

type ToolDef struct {
    Name        string
    Description string
    InputSchema json.RawMessage // JSON Schema 原文
}

type Request struct {
    System      string    // ← 顶层独立字段，不塞进 Messages（见下）
    Messages    []Message
    Tools       []ToolDef // V1 恒空
    Model       string
    MaxTokens   int
    Temperature float64
}

type Response struct {
    Text       string
    ToolCalls  []ToolCall
    StopReason StopReason // end | max_tokens | tool_use | other
    Usage      Usage
}

type Usage struct {
    InputTokens  int
    OutputTokens int
}

type Client interface {
    Name() string // "openai-chat" / "openai-responses" / "anthropic"
    Complete(ctx context.Context, req Request) (Response, error)
}
```

**为什么 `System` 是顶层字段而不是 `Messages[0]`**：Anthropic 要求 `system` 是顶层参数且**不参与** user/assistant 交替；OpenAI Responses 要求 `instructions` 顶层；只有 OpenAI Chat 需要把它塞成 `messages[0]`。把「塞成 messages[0]」这个动作交给 chat 适配器，`chat` 层就永不需要知道协议差异。

**为什么 `ToolCall.Arguments` 是原始字符串**：OpenAI Chat 给的是 `arguments` **字符串**、Responses 给的是字符串、Anthropic 给的是**对象**。统一策略：适配器负责把对象序列化成字符串；解析成结构体的工作由工具调用方（V2 起）做。V1 虽然不用工具，但把这个约定定下来，V2 不用改类型。

### 3.3.2 三种协议的字段映射（实现前照此核对，官方字段随时可能变）

| 维度 | OpenAI Chat | OpenAI Responses | Anthropic Messages |
|------|-------------|------------------|--------------------|
| 路径 | `POST /chat/completions` | `POST /responses` | `POST /v1/messages` |
| 鉴权 | `Authorization: Bearer` | `Authorization: Bearer` | `x-api-key` + `anthropic-version: 2023-06-01` |
| system/指令 | `messages[0].role="system"` | 顶层 `instructions` | 顶层 `system` |
| 输入字段 | `messages` | `input`（字符串或 item 数组） | `messages` |
| 输出长度上限 | `max_tokens` | `max_output_tokens` ⚠️ 名字不同 | `max_tokens`（**必填**） |
| temperature | 0 – 2 | 0 – 2 | **0 – 1** ⚠️ 上限不同 |
| 消息交替约束 | 无 | 无 | **user/assistant 必须交替且以 user 开头** ⚠️ |
| 工具定义 | `tools[].function.{name,description,parameters}` | `tools[].{name,description,parameters}`（**不嵌套 function**）⚠️ | `tools[].{name,description,input_schema}` ⚠️ key 名不同 |
| 工具结果 | `messages` 追加 `{role:"tool", tool_call_id, content}` | `input` 追加 `{type:"function_call_output", call_id, output}` | `messages` 追加 `{role:"user", content:[{type:"tool_result", tool_use_id, content}]}` ⚠️ 最特殊 |
| 文本响应位置 | `choices[0].message.content` | `output[]` 里 `type="message"` 的 `content[]` 里 `type="output_text"` 的 `text` | `content[]` 里 `type="text"` 的 `text` |
| 工具调用响应位置 | `choices[0].message.tool_calls[]` | `output[]` 里 `type="function_call"` | `content[]` 里 `type="tool_use"` |
| 结束原因 | `choices[0].finish_reason` = `stop`/`length`/`tool_calls` | `status`=`completed`/`incomplete` + `incomplete_details.reason` | `stop_reason` = `end_turn`/`max_tokens`/`tool_use` |
| token 用量 | `usage.prompt_tokens` / `completion_tokens` | `usage.input_tokens` / `output_tokens` | `usage.input_tokens` / `output_tokens` |

**三个必须记住的陷阱**：

1. **Responses 的 `output_text` 字段在原始 HTTP 响应里不存在**。它是 OpenAI 官方 SDK（Python/JS）在客户端派生出来的便捷字段。我们直接用 `net/http`，必须自己遍历 `output[]` 提取文本。
2. **Chat 的 `message.content` 在返回工具调用时为 `null`**。Go 里用 `*string` 或 `json.RawMessage` 接，别用 `string` 直接接（会得到空串，分不清「空回复」和「只有工具调用」）。
3. **Anthropic 的 `max_tokens` 必填、`temperature ≤ 1`**。配置里若沿用 OpenAI 习惯填 `temperature: 1.5`，Anthropic 会直接 400。适配器应做范围钳制并在日志里 warn。

### 3.3.3 V1 就要把三个适配器都写完，即使只用其中一个

理由：V1 无工具调用，三个适配器只有「请求/响应字段映射」这点机械工作量。但**如果 V1 只写一个，V2 加工具时三个适配器的转换层都要返工**（尤其是 Anthropic 的 `tool_use`/`tool_result` 是 content block，与 OpenAI 的 role 机制完全不同）。

对照实现建议：先写 `openai-chat`（最简单），再写 `anthropic`（差异最大，写它能暴露中性模型的表达力是否够），最后写 `openai-responses`（结构最特殊）。

### 3.3.4 连接层（`llm/retry.go`、HTTP client）

| 项 | 决定 | 理由 |
|----|------|------|
| HTTP 客户端 | 每个适配器**各自持有**一个 `*http.Client`（不要全局共享单例） | 便于单测用 `httptest.Server`；超时可分别配置 |
| 超时 | 总超时 60s（`http.Client.Timeout`），其中 ctx 由 `chat` 传入并可更短 | 模型慢 + 工具调用（V2）需要余量；但被动窗口是 60min，不至于超窗口 |
| 重试 | 只重试「可重试」错误：网络错误、超时、429、5xx、200 但空 choices | 400/401/403 = 配置错误，重试无意义还会烧配额 |
| 退避 | 1s → 2s → 4s，**最多 3 次尝试**（V1） | 旧方案是 1→2→4→8→16 共 5 次，最长 31s + 请求时间；单聊体验上过慢，且失败后用户已等太久 |
| 429 特殊处理 | 若响应带 `Retry-After`，采用它（但受 ctx 上限约束） | — |
| 错误分类 | 适配器把 HTTP 错误映射为 `llm.ErrAuth` / `ErrRateLimited` / `ErrRetryable` / `ErrContextTooLong` | `chat` 层据此选择**面向用户的文案**，不泄漏 provider 原文 |

## 3.4 `chat` 内部接口

### 3.4.1 Service（生命周期）

```go
package chat

type Service struct { /* 私有字段 */ }

type Deps struct {
    Provider platform.Provider
    LLM      llm.Client
    Store    Store          // 接口，见 3.4.3
    Clock    func() time.Time // 注入时钟，便于测「上下文时间前缀」和回合过期
    Log      *slog.Logger
    Cfg      func() config.ChatConfig // 每次读取最新配置（热重载生效）
}

func New(deps Deps) *Service
func (s *Service) Run(ctx context.Context) error // 消费 provider.Events()，直到 ctx 取消
```

- `Cfg` 是**函数**而不是值：热重载后无需重建 Service（这是「配置热更新」在类型层面的落地方式）。
- `Clock` 注入是为了让「最近 10 轮」和「时间前缀」可测。

### 3.4.2 Pipeline（单条消息的处理步骤）

```go
type Step interface {
    Name() string
    // Process 返回 handled=true 表示已处理完（不再执行后续步骤）
    Process(ctx context.Context, req *Request) (handled bool, err error)
}

type Request struct {
    In     platform.IncomingMessage
    Reply  *platform.ReplyRef
    Trace  string          // trace_id
    ConvID int64           // store 里的会话主键
    TurnID int64           // store 里的轮次主键
    // ... 步骤间传递的中间结果
}
```

V1 的步骤链（只有一步）：`[aiStep]`
V2 的步骤链：`[commandStep, aiStep]` —— 命令命中即 `handled=true`，**不入 AI 上下文**（见 R4）
V3 在 `commandStep` 里增加 `/cron` 子命令；定时任务由**独立引擎**触发，不走 pipeline（它是出站主动消息）

### 3.4.3 Store 接口（在 `chat` 包内声明，由 `store` 实现）

Go 的惯例：**接口定义在使用方**。所以 `chat` 声明自己需要什么，`store` 包不需要暴露接口。

由此得出一条明确的依赖方向：**`store` 会 import `chat`（为了使用 `Turn` / `TurnRef` / `TurnParams` / `Event` 这些类型），而 `chat` 绝不 import `store`**。这不是循环依赖，而是端口/适配器的正常形态 —— 适配器依赖核心，核心不感知适配器。同样地，`platform/provider/*` 与 `llm/provider/*` 也可以 import 它们各自端口包的类型。

```go
// internal/chat/store.go
type Store interface {
    GetOrCreateConversation(ctx context.Context, key platform.ConversationKey, s platform.Sender) (convID int64, err error)

    // BeginTurn 开启一轮。
    //   - 不是重复推送：写入状态为 processing 的轮，返回 TurnRef{IsNew: true}
    //   - inbound_msg_id 已存在：不写入，返回既有轮 TurnRef{IsNew: false}，
    //     由调用方按 R15 的规则决定「跳过」还是「接管重试」
    BeginTurn(ctx context.Context, p TurnParams) (TurnRef, error)

    // FinishTurn 结束一轮（写入 assistant 消息并把状态从 processing 改为终态）
    FinishTurn(ctx context.Context, turnID int64, status TurnStatus, assistantText string, usage llm.Usage) error

    // RecentTurns 取最近 n 轮**有效**对话，按时间正序，每轮含其全部消息
    RecentTurns(ctx context.Context, convID int64, n int) ([]Turn, error)

    // StaleTurns 返回 finished_at IS NULL 且 started_at 早于 olderThan 的残轮
    // （启动时用于日志提示；也是 R15 中「接管重试」判定的数据来源）
    StaleTurns(ctx context.Context, convID int64, olderThan time.Duration) ([]TurnRef, error)

    AppendEvent(ctx context.Context, e Event) error
}

// TurnStatus 是**轮**的状态（不是单条消息的状态，见 §4.2）
type TurnStatus string
const (
    StatusProcessing TurnStatus = "processing" // 中间态：已建轮、尚未出结果（崩溃恢复的判据，见 R15）
    StatusOK         TurnStatus = "ok"         // 有效轮，进上下文
    StatusFailed     TurnStatus = "failed"     // 失败轮，不进上下文但可审计
    StatusFiltered   TurnStatus = "filtered"   // 非文本 / 命令轮，不参与上下文
)

type TurnParams struct {
    ConvID    int64
    MsgID     string          // 平台 inbound_msg_id（幂等键）
    Sender    platform.Sender
    UserText  string
    TraceID   string
    StartedAt time.Time
}

type TurnRef struct {
    ID        int64
    IsNew     bool          // false = 幂等命中（同 msg_id 已存在）
    Status    TurnStatus
    StartedAt time.Time
}
```

`BeginTurn` / `FinishTurn` 成对出现，是为了让「一轮」有明确的数据库边界（见 §4.3），也保证**AI 失败时这一轮仍以 `status=failed` 落库**（可审计，但不出现在 `RecentTurns` 里）。

`BeginTurn` 返回 `TurnRef` 而不是裸 `turnID`，是为了让「重复推送」这个分支**必须在调用点被显式处理**（`IsNew == false`）—— 否则很容易写成「拿到 ID 就继续跑」，于是重复推送与崩溃恢复（R15）两件事都会被静默做错。

## 3.5 配置接口与「热重载等级」

`config` 包对外只暴露三件事：

```go
func Load(path string) (*Config, error)   // 解析 YAML + 环境变量覆盖 + 默认值 + 校验
func (c *Config) Validate() error         // 启动时和 reload 时都调用
func Diff(old, new *Config) ChangeSet     // 变更分类，见 §5.2
```

**关键约束**：`config` 包**不许** import 任何其它内部包（不许 import llm、platform、store）。它只做数据。

「谁响应配置变更」由组合根决定：

```go
// cmd/botd/main.go 里注册订阅
cfg.OnReload(func(old, new *config.Config, cs config.ChangeSet) {
    switch {
    case cs.Has("llm"):        // 可热载：重建 llm.Client / 更新其配置
        swapLLM(new.LLM)
    case cs.Has("platform"):   // 不可热载：只记 warn，提示需 restart
        log.Warn("platform 配置已变更，需执行 /admin/system/restart 才能生效")
    }
})
```

这样 `config` 不知道 `llm` 的存在，依赖方向保持单向（见 §2.1）。

## 3.6 错误与文案分层

三层的错误**不许混用**：

| 层 | 类型 | 例子 | 谁消费 |
|----|------|------|--------|
| 适配器层 | 哨兵错误 | `platform.ErrReplyQuotaExhausted`、`llm.ErrAuth` | `chat` |
| 编排层 | `chat` 的错误分类 | 「模型鉴权失败」「模型限流」「上下文过长」「平台发送失败」 | 文案映射 |
| 用户可见层 | 自然语言 | 「❌ 模型服务暂时不可用，请稍后再试」 | QQ 用户 |

规则：
- **用户文案里不许出现** HTTP 状态码、API 原始错误体、base_url、key 片段
- 但**日志里必须有**全部原文（含 trace_id），否则排障无门
- 用户文案集中在 `chat/errors.go` 一张 map，便于统一改语气

（旧 TS 版有专门的 `ai/error-copy.ts` 做同一件事，可参考它的分类与文案风格。）
